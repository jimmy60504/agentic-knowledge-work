## 主題一：地震業務的工作型態

目的是讓學員在聽任何 Agent 的東西之前，先看見自己的工作長什麼樣。

**開場。** 說明下午要拿自己的工作來試作，看 Agent 能接手哪一段、值不值得試。要能判斷這件事，先要知道 Agent 拿到一句話之後中間做了什麼，才變成一份投影片、一封信或一張工單。上午先把這個過程攤開，再對回地震業務。講完以後，學員手上會有一張表可以自己填。今天不是要說中心該導入什麼，也不是說哪個科的工作可以自動化。

**十種工作動詞。** 依 [工作類型筆記](../kb/reference/cwa-earthquake-center/cwa-earthquake-center-work-types.md)：守視發現、查核判定、通報發布、回答解釋、提供資料、整理保存、分析研究、維護設備、維護系統、規劃管考。每個動詞列實際工作、輸入與產物、相近的外部工作語意。說明這是公開職掌與年報的歸納，不是 SOP，請學員當場修正。修正本身就是互動，也把限制講清楚了。

**案例：測站異常待查。** 從讀取狀態、比對基準與維修紀錄、人員確認、建工單通知、追蹤回存走一遍，標出每一步是哪個動詞：守視接到維護與協調，再接到整理與保存。結束時學員手上有一張動詞表和一條工作鏈。

接口：案例交給後面四個主題共用；動詞表在主題五回收成七欄表的「業務動詞」欄。

## 主題二：Agent 的運作機制

目的是建立對機器的正確想像，避免把「寫出指令」當成「做完了」。

**共同工作環境。** 使用者提出「文件櫃、工作台、機器人、加工機器」的比喻。文件櫃保存可取用的材料，工作台放正在修改的草稿；機器人依指派查找、討論、記錄與製作；加工機器依明確規則製作與重複執行。

| 環境 | 在這門課的例子 | 為什麼需要它 |
|---|---|---|
| 文件櫃 | `kb/` 的來源、筆記、洞見 | 材料找得回，也能補充與更正 |
| 工作台 | `drafts/` 的論述、提案與逐頁稿 | 可以先看結構、討論與重排，還不用完成最後版面 |
| 機器人 | agent | 查閱材料、提出建議、記錄決定、起草與操作工具 |
| 加工機器 | 程式、既有軟體、執行環境或設備 | 依明確規則製作與重複執行 |
| 成品 | 文件、簡報、報表、程式或實體 | 交給實際使用者檢查是否合用 |

人工、數位化與 Agent 化三種方式並存：人親手做；人操作軟體或程式做；人與 agent 討論，由 agent 操作工具做。有些問題靠資料整理、一般軟體或流程調整就能解決，不必說成嚴格先後階梯。

**循環。** 模型主要產生文字形式的內容與動作描述，可能是一段指令、程式碼，或符合工具規格的結構化呼叫。它本身沒有手去按滑鼠，也不會只因為寫出「寄信」兩字就真的寄出。執行框架預先接好可用工具與執行規則：收到模型的工具呼叫後檢查權限，交給對應的程式執行，再把結果送回模型；模型依結果提出下一步。

```text
人的目標／事件
    ↓
模型讀取文字脈絡，產生回答或工具呼叫（名稱＋參數／指令）
    ↓
執行框架呼叫預先接好的工具：終端機、程式、API、瀏覽器、滑鼠等
    ↓
工具真的讀取、計算、點擊、寫入或傳送，回報結果／錯誤
    ↓
模型依回饋繼續操作、請人確認，或交付成果
```

**最小例子：建立一個 Markdown 檔。** 模型先決定檔案放哪裡、叫什麼、寫哪些內容，必要時先呼叫工具查目錄；產生 Markdown 文字並提出「建立這個路徑的檔案」的工具呼叫，這一步仍只是文字與參數；執行框架交給檔案工具或終端機，底層程式真的寫入位元組；工具回傳結果，模型再讀檔確認檔案存在、內容正確。單獨的模型可以寫出 Markdown 內容，無法僅靠生成文字在本機建立檔案。投影片同理：模型先寫逐頁稿與程式，執行框架跑程式產出 PPTX，再開檔檢查；細節留給主題五。

**回到案例。** Agent 查日誌是讀取工具，建待查卡是寫檔工具，建工單是呼叫 API，通知是傳送工具。每一步都可以分成提出動作、執行動作、驗證結果三件事。

十二類操作表不進投影片，留作工作坊七欄表的附錄。

接口：「提出、執行、驗證」在主題五變成三條界線；工具往返留下的檔案在主題三成為中間產物的來源。

## 主題三：協作方法：中間產物與對齊

目的是給學員一個拆工作的方法。核心只有一件事：中間節點 C 是什麼、怎麼找、找到後誰檢查什麼。

**思考外部化。** 人心裡的想法轉成文字、口述與畫面時經過選擇與組織；對方看到的是表達，無法直接取得完整意圖。協作因此需要一個可共同查看的中間產物。先請 agent 把目前理解整理出來，人才能指出哪裡漏掉、誤解或還沒決定。人的想法也會隨新材料與試做結果改變；回饋是在共同釐清，不只是把模型拉回第一次說法。

保留使用者要求記下的表述：

> LLM 學過大量人類語言與互動模式。我們可以借用溝通、管理與教練的方法，把意圖、背景、分工與標準說清楚，提高它產生合適回應的機率。

互動像同事或教練，不代表模型具有人的動機或責任；是否對齊意圖與事實是否正確，要分開檢查。可用的三分鐘短示範：先說零散想法，請 agent 寫成一段，現場指出一個偏移，補充理由並重寫。

**A→C→B。** 先看目前有什麼 A、希望得到什麼 B。若不能清楚交代或可靠完成 A 到 B 的轉換，就找中間節點 C，把工作拆成 A → C → B。C 可以是資料、決定、規格、草稿或試作結果；它要補上一個具體缺口，讓下一步有依據，也讓人能檢查。加入多少層取決於任務、人的理解與工具能力；同一層可以反覆修改，不必把每輪對話都變成新流程。

| 目前卡住的地方 | 候選中間產物 | 人檢查什麼 |
|---|---|---|
| 想法直接變簡報，主張與順序還不清楚 | 結構化文稿 | 背景、目的、主張與依據是否成立 |
| 文稿轉成簡報，還不知道每頁的用途 | 逐頁稿或 ghost deck | 邏輯能否連讀、證據與口述放在哪裡 |
| 觀測清單直接判定故障，替代解釋還沒排除 | 與基準及維修紀錄的差異表 | 資料中斷是設備故障還是通訊中斷，證據夠不夠 |

前兩列延續第二週，第三列是本週案例。第二週的三圈就是三個 C：文稿、逐頁稿、成品，定義以 [ssot v3](../ssot/three-loops.md) 為準，本週用一句話帶過，不另講三圈的定義與來歷。第二週發布版本第一圈仍稱「確認方向」，只需簡短交代改名理由。

找 C 的來源不只一種：問 AI、請 AI 搜尋、自己讀資料或請教他人、觀察現場與親自試做。新發現可能連 A、B 的定義都改變。先把 agent 的建議當候選，再用材料或試作確認。成品出現內容問題時，回到適當的草稿層修正，不是每次都在版面上重做。

**C 裡面的內容要分清來源。** 材料進入思考時，四種內容分開保存，摘要不等於讀過：

| 內容類型 | 保存時說清楚什麼 |
|---|---|
| 原始材料與作者主張 | 來源在哪裡、原文支持什麼、有哪些條件 |
| 對作者意圖的推論 | 根據哪些線索推論、哪些部分不確定 |
| 自己的新洞見 | 加入了什麼經驗與判斷、與原文有何關聯 |
| Agent 的提案 | 哪些仍是候選，需要用什麼驗證 |

蒸餾是依用途取捨，不只是縮短字數。摘要可能漏掉方法、限制或關鍵例外；當結論要拿來支持決定、摘要與理解衝突，或想深入找新問題時，回讀原文。這與 [孫以瀚講座筆記](../kb/reference/sun-ai-assisted-research-writing-lecture.md) 對摘要與深讀的區分相呼應，只取此觀點。用自己的長文檢查 Agent 摘要的練習已移至[後半工作坊](04-week4-agent-value-workshop.md)備援題，課堂不做。

**案例落點。** 從觀測清單到待查卡之間，缺的 C 是差異表；沒有它就不能判斷是設備故障還是通訊中斷。

接口：C 就是主題二裡工具往返留下的檔案，也是主題四要決定存放位置的東西，也是主題五七欄表的「中間產物」欄。

## 主題四：分工與知識回存

目的是讓學員知道一件工作做完要留什麼、留在哪裡，下次才能接著用。三個部分各回答一個問題。

**請教與交辦：這一步要 Agent 做什麼。** 請教時帶著自己的經驗和意見，讓 agent 提供不同方向與關鍵字；交辦時說明目的、希望完成的結果、重要限制與檢查標準，保留具體做法的選擇空間。同一個 Agent 在一件工作裡會輪流扮演幾種工作角色：

| 此時需要的角色 | 可以請它做什麼 |
|---|---|
| 討論者 | 拓展選項、比較方向、指出還沒想清楚的部分 |
| 資料蒐集與整理者 | 查找來源、取用舊筆記、整理關聯與差異 |
| 記錄者 | 留下共識、決定理由、未定事項與下一步 |
| 審查者 | 找反例、缺乏依據的假設與讀者可能誤解的地方 |
| 起草者 | 把零散想法整理成可閱讀、可修改的草稿 |
| 工具製作者與操作員 | 建立或修改程式、操作工具、檢查實際輸出 |

這些是工作角色，不要求多開六個 agent，也不保證換角色稱呼就會提高品質。審查建議仍要對照依據。

**模糊交 Agent，明確交程式：這一步該由誰重複做。** 保留使用者的分工想法：

> 讓 agent 去處理模糊不確定的東西，然後把明確規則收斂成程式碼讓他可以重複執行。

需要理解材料、提出選項與試做的工作交給 Agent 探索；規則確定後收斂成程式或既有工具，可以反覆執行、結果穩定。課程自己的例子是先讓 Agent 把逐頁稿討論定，再用一支程式把逐頁稿產成 PPTX；內容有問題改逐頁稿，版面有問題改程式，不在成品上手工修。程式化有編寫、維護與執行成本，Agent 也可以直接操作既有軟體，不必每件事都寫程式。驗收看實際成品，不以程式沒有報錯就認定完成。

**材料、草稿、決定、標準各存在哪裡：下次怎麼接得上。** 先問一件工作需要保存什麼，再介紹位置，不要求學員一開始複製整套資料夾。完整結構以 [專案結構正本](../ssot/project-structure.md) 為準。

| 過程中需要留下什麼 | 本課採用的位置 | 要解決的問題 |
|---|---|---|
| 還沒採用的想法與問題 | 對話、工作紀錄待消化區 | 不讓未定想法混入成品 |
| 材料、來源與自己的洞見 | `kb/` | 找得回依據，分清原文與延伸 |
| 為本次任務組合的內容 | `drafts/` | 有一份可以反覆收斂的工作稿 |
| 人確認可交付的內容 | 正式文件與成品 | 使用者能拿去使用 |
| 多份內容共用的已定概念 | `ssot/` | 避免相同概念各自改成不同版本 |
| 確認有效的做法與標準 | `AGENTS.md`、`skills/` | 下次能依同一標準工作 |
| 為什麼採用、放棄或修改 | `工作紀錄.md` | 換次討論後仍能理解取捨 |

Agent 可協助找舊材料、提出關聯、保存修正，但來源、分類、有效版本與適用條件仍需人確認。整理不是越多越好；要能從檔案回到工作，並更正過時或錯誤內容。可用的三分鐘短示範：把一個有效標準回存，再換一個新需求，展示如何取用先前材料與決定。

**案例落點。** 比對基準的規則確定後寫成腳本定期跑；異常原因與解法回存到紀錄；「哪些訊號不算故障」這類確認有效的標準寫進工作規則。

接口：角色分工對應主題五「人核准哪一步」；規則交程式對應主題五第三種接手方式「建工具後退出」；保存位置對應工作坊操作引導四「這次試過什麼、留下什麼」。

## 主題五：接手範圍與盤點表

目的是給學員判斷「哪一段可以交出去」的眼光，並交付下午要用的表。依 [產出方式筆記](../kb/tools/agent-output-modes.md)與[四層對照筆記](../kb/tools/agent-operation-output-business-map.md)。

**九類產出，收成三組。** 給人看的內容、給系統用的資料、可執行的程式、支持判斷的分析、留給下次的工作資產，主要留下可審查的內容或檔案；已完成的系統操作與已送達的通知，改變外部系統或人的工作狀態；持續監看是運行中的服務；即時答覆在對話中逐次回應。這些類別在同一任務中可以串起來：先產生差異清單，經人確認後建立工單，再通知承辦人。

**三條界線。** 寫出指令不等於執行成功；給建議不等於做決定；發出通知不等於對方收到並接手。

**六種接手方式。** 用同一個測站異常比較：

| 接手方式 | Agent 接手到哪裡 | 測站異常的例子 |
|---|---|---|
| 人向 Agent 請教 | 人在正式流程之外發問，Agent 回答後退出 | 同仁問斷訊的可能原因，拿待查清單自行排查 |
| Agent 完成一次性交付 | 用工具查找、寫檔、驗證，交出檔案後退出 | 產出一份測站異常彙整報告或分析用的 CSV |
| Agent 建置工具後退出 | 建置時產生程式或規則，之後由一般程式執行 | 寫好資料缺漏比對腳本，之後排程固定執行 |
| 固定節點呼叫一次模型 | 既有程式把輸入送給模型取回結果，照固定路徑走 | 系統把故障描述送去抽測站編號，再交原流程 |
| 流程節點呼叫 Agent | 事件到達時 Agent 查資料、選工具、迭代，交給下一節點或人 | 新異常觸發 Agent 查日誌與維修史，做待查卡交值班者 |
| Agent 協調跨節點工作 | 按回饋選擇下一步，跨系統查找、建待辦、等核准並追蹤 | 從查證、建單、通知到追進度由 Agent 串接 |

重點是這不是按數字遞增的能力等級：建置時接手很多工作，也可能讓 Agent 在運行時完全退出。接手範圍與寫入權限要分開看；第四種有模型參與但不能選工具與下一步，不必稱為 Agent。這些用法可以先後相接。

**七欄盤點表。** 觸發、資料、具體操作、中間產物、產出、業務動詞、驗收人。當場用測站異常填一次。每一欄都在前面出現過：觸發與操作來自主題二，中間產物來自主題三，業務動詞來自主題一，驗收人來自主題四的分工。

外部組織把 Agent 放在客服、知識檢索、文件抽取、事件分流等位置，一句帶過；完整的缺口類型留給工作坊學員找自己的缺口時對照，避免開場就講二手案例。

**銜接工作坊。** 學員各選一件工作，先以工作坊的五欄表攤開整件工作的現況，再以七欄表拆出一段。價值、成本、風險與實作條件的完整操作引導只放在後半稿。
