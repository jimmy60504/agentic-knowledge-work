## 概念串接

1. 承接第五週，以講師手上的題目為例：品質檢查是組內存在已久的問題，資料一再被退回，想看看 AI 能不能幫忙。
2. 先用 AI 做一個原型，這是 vibe coding 的示範；整個過程都還在需求階段，先把畫面做出來，確認完成的樣子合不合理；對畫面的想像從第一天就以文字寫下。
3. 分析現況：流程仰賴人工又反覆退回，優化目標放在減少來回次數，方向是在提交前攔截錯誤；從自己執行時的阻礙，寫出好的設計要滿足的條件；先假設每一步都出錯，分出三層攔截；工具必須減少工作而不是監控。
4. 釐清需求：Story 圖用來看出人與系統之間的交互，要抽象到能聚焦問題；現況圖從逐項列出，收成「檢查項目列表、後續處理、迭代到可以上交」，才看出最大的缺口是定位完就能上交，錯誤流到下游；向同仁確認後得到兩項新資訊：派工網頁成為必經的檢查節點，同一組讓方案的區分取消。
5. 製作原型：先建立開發環境、盡量還原生產環境，以真實的資料與程式跑一次，暴露投影片沒寫的問題；再做雛形，再對齊現有介面，最後加強可讀性；三個設計目的：讓承辦不必重新學習（導正回單筆提交、設計語言與現有系統一致，以截圖與 Agent 溝通）、讓檢查的依據清楚一致（規則單一來源、網頁只說明、規則要能溯源）、讓承辦能自己確認檢查結果（列表的快速摘要、詳細檢視的逐一對照）。
6. 與 Agent 合作：資訊越多，設計越貼近現實，人類工程師也一樣；軟體開發的時間大多在理解需求與設計架構，Agent 幫忙的主要是實作。
7. 之後的路：原型、自己用的小工具與正式工具三層，本週到自己用的小工具為止；正式工具要補工程化，功能分階段放大，以前測與後測評估效果，長期在上游補上防呆；下週進入規格階段。

## 一、分析現況

### 7. 段落頁：分析現況

- 標題：分析現況【無原話】
- 畫面：路線圖，標出第一階段。

### 8. 現況：仰賴人工，反覆退回

- 目的：交代現況的問題。
- 標題：除了仰賴人工，還一直反覆退回，地震沒有辦法快速消化
- 原話：「整個流程除了仰賴人工，然後一直反覆的退回，導致地震沒有辦法快速消化」（10/06）；「現在 qc 流程都還是大量仰賴人工，然後需要被重新處理的［定位結果檔］有點多」（10/06）；「實際上的流程比較像是主管派發地震給同仁，然後 qc 本身還是人自己做」（09/30）
- 畫面：派發、定位、自行檢查、主管檢視、退回的流程圖（文稿第二段的 mermaid 圖上半部），標出人工檢查與退回的位置。

### 9. 優化的目標：減少來回的次數

- 目的：說明要以什麼評估改善，以及為什麼不是件數。
- 標題：把優化的目標放在實際來回的次數
- 原話：「我自己覺得是 kpi 定在數量造成的問題，那我們現在要把優化的目標實際上來回的次數來評估，看能不能減少現在這種提交錯誤率降不下來的問題」（10/06）
- 畫面：兩種衡量方式對照：以件數計算工作量，與以來回次數評估品質。
- 備註：措辭放在制度設計（以件數計算工作量，讓人傾向先送出再說），不指向個人。對應第五週「以返工作為驗收標準」，也是第五段前測與後測的指標。

### 10. 在提交前攔截錯誤

- 目的：說明達成目標的方向。
- 標題：讓錯誤在提交前就盡量被流程攔截
- 原話：「要達到這個目的就是要讓錯誤在提交前就盡量被流程攔截，才不會在需要比較久的同仁之間的傳遞上面一直來回」（10/06）
- 畫面：兩條時間軸對照：承辦送出前自己修正，與經主管檢視後退回再修正，標出同仁之間傳遞所需的時間【待畫】。
- 備註：同仁之間的每一次傳遞都要等待，錯誤越晚被發現，來回的成本越高。

### 11. 實際執行時的阻礙

- 目的：從講師自己的經驗說明檢查為什麼常被略過。
- 標題：拿到投影片也要花很大功夫，送出前懶得一個一個照著做
- 原話：「我自己拿到那個投影片，也是要花很大功夫才會大概知道他在寫什麼，然後送出去之前也很懶得把那個資料來源打開來一個一個照著做」（10/05）
- 畫面：訓練投影片與紙本清單的照片（遮蔽）。
- 備註：以講師自己若要完整執行會遇到的阻礙來說，不推論同仁的心態（使用者 10/05）。

### 12. 好的設計要滿足的條件

- 目的：寫下之後檢視每一版成品的標準。
- 標題：很快知道哪裡不對、知道怎麼改、不用感覺被監視
- 原話：「是不是有辦法設計一個 qc 清單，讓操作的人可以很快知道哪裡不對，還有知道怎麼改，就是有個明確的指示，然後操作起來又不會跟原本的習慣差太多，也不會很難上手，還有不要感覺是一個被監視的東西，用起來大家都可以輕鬆一點，那這就會是個好的設計」（10/05）
- 畫面：五個條件的條列。
- 備註：對應第五週的需求工程：先確認成功的條件，再決定做什麼。

### 13. 分層攔截：如果全部都錯

- 目的：說明哪些錯誤交給程式、哪些交給人。
- 標題：如果全部都錯，有多少東西沒有被原本流程攔截
- 原話：「最重要的就是看如果全部都錯，可以有多少東西沒有被原本流程攔截，變成跑到下一個承辦身上需要檢查」（09/29）；「感覺有點醜，還是你畫只有資料處理流程，然後全部都錯的情況他走了所有的東西，因為我們應該重點在要攔截所以他沒做的事情」（09/29）
- 畫面：三層的示意：規則攔截、物理限制篩選、人工檢視【待畫】。
- 備註：口述三層的例子；這個分層由講師提出，之後成為工具的骨架。

### 14. 工具的定位

- 目的：說明工具能不能被使用的關鍵。
- 標題：不是一個監控程式，而是一個真的幫忙減少工作的程式
- 原話：「那就要這個程式不是一個監控程式，而是一個真的幫忙減少工作的程式，這樣才會有機會被普遍使用」（09/29）
- 畫面：大字引言。
- 備註：結果先給承辦本人，不自動回報，也不統計個人錯誤。

### 15. 貼近原本的流程

- 目的：說明另外兩項同一天的決定。
- 標題：不要大幅改動原本大家熟悉的流程
- 原話：「check list 應該要貼近原本 ppt 的步驟，就是不要大幅改動原本大家熟悉的流程，就是有個原本就有依據的文件源頭去比對」（09/29）；「第一版可能先不要去測試 ui，就是想辦法用指令的方式去跑，UI 部分就是提示人類要去做」（09/29）
- 畫面：兩項決定並列。
- 備註：這三項決定來自對業務、同仁處境與現有環境的理解，Agent 無法自行提出。
## 二、釐清需求

### 16. 段落頁：釐清需求

- 標題：釐清需求【無原話】
- 畫面：路線圖，標出第二階段。

### 17. Story 圖的用途

- 目的：說明現況圖要抽象到什麼程度。
- 標題：看出每個人或系統之間的交互關係，模型不能 1:1 反映現實
- 原話：「story 圖該怎麼使用，就是他的目的是要看出每個人或系統之間的交互關係，那模型本身不能太複雜到 1:1 去反應現實，要某種程度的抽象，來聚焦到要解決的問題上」（10/06）
- 畫面：第四週介紹 Story 圖的簡圖（演員、工作物件、活動），旁邊註明「抽象到能聚焦問題」。
- 備註：回扣第四週。

### 18. 一開始照著規則一個一個列出來

- 目的：說明第一版現況圖的問題。
- 標題：一開始照著規則一個一個列出來，看不出實際上的重點
- 原話：「現況圖大致上的過程應該會是一開始 agent 就是照著規則一個一個列出來，所以會看起來很雜亂，也看不出實際上的重點」（10/05）
- 畫面：開發截圖中逐項列出的故事圖（重畫）。

### 19. 收成大步驟，才看到資料來回

- 目的：說明抽象層級如何讓問題浮現。
- 標題：不用把檢查規則一一列出，抽象成一個 QC 項目列表與後續的流程
- 原話：「我們這邊就是變成表現出針對不同系統的交互的階段，那就會不用把具體檢查的規則一一列出來，只要抽象成有個 qc 的項目列表要檢查，然後配套會有哪些後續的流程，然後一直迭代到沒有問題或是需要變成特殊案例處理，就可以上交」（10/06）；「後來是有重新整理成比較大的步驟，把所有同一個步驟都隱藏起來，才會看到實際上資料來回的樣子」（10/05）；「我覺得圖好像可以再更簡單？」（09/30）；「那個人跟程式中間還是要多一個動詞？還是介係詞？」（09/30）
- 畫面：收成迴圈之後的故事圖（重畫），與前一頁的逐項列出左右對照；迴圈標出「檢查、後續處理、迭代到沒有問題或轉為特殊案例、上交」。

### 20. 目前最大的缺口

- 目的：指出分析現況後找到的缺口。
- 標題：定完地震就可以先上交，沒檢查的東西都跑到下面的步驟
- 原話：「分析現在的流程就是會發現原本定完地震後就可以先上交，那就很多沒檢查的東西就會跑到下面的步驟，為了減少下游的工作量，才會要有流程攔截這些錯誤，這個就是目前最大的缺口」（10/06）；「原本也有兩個［檢查程式］了，只是沒有變成流程上必經的節點，全部靠人本身去完成」（10/05）
- 畫面：現況故事圖上標出缺口：定位完成到上交之間沒有必經的檢查，錯誤流向主管檢視。
- 備註：定位軟體缺少防呆，既有的檢查程式也不是必經節點；這個缺口正是第 10 頁「在提交前攔截」要補上的位置。

### 21. 照規定做完要走過的步驟

- 目的：說明檢查常被省略的原因在於步驟繁瑣，而不在個人。
- 標題：照規定做完，要走過一大堆繁瑣的步驟
- 原話：「第二張圖比較像是要去畫一個流程是要走過一大堆繁瑣的步驟」（10/06）
- 畫面：三張遞進的故事圖並排（重畫）：現況、假設承辦以現有工具完整自行檢查、導入之後；第二張標出繁瑣之處：分別執行數支檢查程式、對照紙本清單補查、逐筆依經驗判斷、改完再重跑直到清單清空。
- 備註：口述帶過一句：即使全部照做，有些項目舊程式本來就檢查不到。呼應第 9 頁，問題出在衡量方式與工具，與個人是否認真無關；學員畫自己的現況圖時，也可以多畫一張「照規定完整做完」的版本。前後修改約二十次才收斂為這三張圖。

### 22. 向同仁確認後的兩項新資訊

- 目的：說明新資訊如何決定工具的位置，並印證第五週「需求需要詢問才能釐清」。
- 標題：派發地震事件的網頁可以變成一個自動化的節點
- 原話：「得到一個新資訊，他們有個派發地震事件的一個網頁，那這個 qc 原本是人工做，這裡感覺就是可以變成一個自動化的節點去提示，檢查清單也可以跟網頁整合」（09/30）；「而且……資料處理跟目錄維護基本上是同一組」（09/30）；「那這樣就沒有什麼方案一跟二的差別了」（09/30）
- 畫面：兩欄：左欄「派工網頁」，配文稿第二段的流程圖（現況與導入後），標出上傳時自動檢查的位置；右欄「同一組」，原本並列的兩種方案劃掉其一。
- 備註：兩項資訊都是向同仁了解實際作業後才知道的。前者決定了檢查節點的位置，後者讓原本的兩種方案整段取消。

## 四、與 Agent 合作的方式

### 32. 段落頁：與 Agent 合作的方式

- 標題：與 Agent 合作的方式【無原話】

### 33. 資訊越多，設計越貼近現實

- 目的：歸納整個過程中方向調整的原因；人類工程師也是如此，一句帶過。
- 標題：越多的資訊就會得到越貼近現實的設計
- 原話：「這些轉折其實也是像我們要跟 agent 溝通一樣，越多的資訊就會得到越貼近現實的設計，人類工程師也是需要通靈才能先完成階段任務，然後獲得新資訊重新對齊後就會修正」（10/05）

### 34. 力氣花在哪裡

- 目的：說明軟體開發的時間大多花在理解需求與設計，Agent 幫忙的主要是實作；並以逐階段的對照總結人與 Agent 的分工。
- 標題：軟體開發大部分時間在理解需求跟設計架構，Agent 幫忙的是實作
- 原話：「軟體開發大部分時間其實是在理解需求跟設計架構，那 agent 實際上幫忙的是實作，也就是很多人對於軟體工程師的誤解，就以為時間都花在寫程式而已」（10/06）
- 畫面：上半部是長條圖：寫程式之前約八十則訊息、寫程式約三十則【待畫】，旁邊一行「理解需求與設計架構 → 實作」，標出 Agent 主要幫忙的位置。下半部是三個階段的對照表，兩欄為「Agent 做了什麼」與「人判斷了什麼」：
  - 分析現況：Agent 把投影片整理成文字與步驟清單、依方向重畫故事圖、分析舊程式的類型；講師寫下好的設計條件、提出三層攔截、確立不監控、決定貼近原流程與只用指令。
  - 釐清需求：Agent 重畫每一版故事圖、分析防呆缺口、整理要確認的問題、依新資訊改寫文件；講師決定哪一版圖可以討論、向同仁確認分工。
  - 製作原型：Agent 寫出掃描程式並統計、撰寫規則檔、網頁、圖表與測試，數分鐘內做出新版，比對原始碼，以真實資料確認結果不變，量測效能（一天約一百三十個檔案不到 0.1 秒）；講師取得資料與程式、提供現場畫面與習慣、刪去過大的需求、追問來源。
  - 表格下方一行「回到自己的工作」：主動提供現場的資料、以截圖溝通設計語言、先做出一版再修正、追問依據、先量測再決定。
- 備註：口述先點出常見的誤解：以為工程師的時間都花在寫程式。案例的數字正好說明，程式可以很快完成，前提是需求已經弄清楚、設計已經想好；Agent 讓實作變快之後，理解需求與設計的比重反而更明顯。 對照表說明每個階段真正的決定都在人這一側：Agent 縮短的是製作與查證的時間，人負責判斷。這也回應第五週的三個條件：驗收標準是事先寫下的設計條件與規則檔，外部檢查是原始碼比對、量測與真實資料，判斷與責任由熟悉業務的人承擔。
