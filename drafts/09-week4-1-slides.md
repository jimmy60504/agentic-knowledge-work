**筆記**

這一頁在示範怎麼把一件現有的工作拆開。看一件工作，先問四件事：手上有什麼、要交出什麼、中間要判斷什麼、分成幾步。這張圖用 domain storytelling 的畫法把四件事畫出來：演員是研究者，六個編號活動是步驟，每個活動交出一樣工作物件，材料在起點，成品在終點。

案例是測試一個研究想法。研究者想確認一個想法成不成立，例如新的震度預估方法是否優於現行方法。圖上有四個演員：研究者、文獻資料庫、計算環境、同儕，系統也算演員。七個活動照編號念：研究者向文獻資料庫檢索出論文清單；依論文清單選定主要方法；依主要方法撰寫程式碼；計算環境以歷史資料執行程式碼，產出結果圖表；研究者分析結果圖表，歸納出分析結論；依分析結論撰寫報告；同儕審閱報告，寫出審閱意見。演員換手的地方，程式碼交給計算環境、報告交給同儕，就是要有完成證據與驗收的地方。要決定的是選哪個方法、結果可不可信、結論怎麼下，這三步由人決定。

### 4｜模型與執行框架

**畫面**

- 主訊息：模型只產生文字；接上執行框架，動作才發生。
- 圖：一張圖片，取自 Anthropic〈Building effective agents〉
- 來源：https://www.anthropic.com/engineering/building-effective-agents

**筆記**

圖的任務：左右對比，兩邊是同一個模型。左邊只吐出一張文字，工具灰掉、沒有連線；右邊模型與執行框架來回呼叫與回傳，框架接檔案、程式、網路
版型：對比

先看左圖。模型本身只產生文字，產生的可能是一段回答，也可能是一段動作描述：一行指令、一段程式碼、一個寫明工具名稱與參數的呼叫。它沒有手，寫出計算的程式碼，數字還沒有算出來。

再看右圖。真的讓事情發生的是執行框架。執行框架事先接好可用的工具與執行規則：終端機、程式、API、瀏覽器、滑鼠。模型提出一個工具呼叫，執行框架檢查權限，交給對應的程式執行，把結果送回模型；模型讀到結果決定下一步，繼續操作、請人確認，或交付成果。整個過程是一個循環：人給目標，模型提出動作，工具執行，結果回來，模型再提出下一個動作。

**原話與來源**

- 「一開始先講說他就是用文字的方式，去控制可能像 harness 預先寫好的程式，terminal 或是滑鼠等等，去做到他想做的事情」（09-19 17:49）
- 「4 跟 5 感覺可以合併變成左右比較的兩張圖」「寫出『寄信』不等於寄出 我覺得這個太生硬了」（09-20）

### 5｜最小例子：建立 markdown 檔案

**畫面**

1. 規劃：模型決定位置、名稱與內容，必要時先查目錄
2. 提出：模型產生 Markdown 文字，提出「建立檔案」的工具呼叫；此時仍只是文字與參數
3. 執行：執行框架把呼叫交給檔案工具，程式寫入磁碟
4. 驗證：工具回傳結果，模型回讀檔案，確認位置與內容

- 圖：四張步驟卡片橫排，卡片標題規劃、提出、執行、驗證，各附一個圖示

**筆記**

圖的任務：讓人看出第一、二、四步發生在對話裡，是文字；第三步發生在電腦裡，是磁碟。可用實際請 Agent 建檔的終端機截圖代替
版型：流程

用最小的例子走一遍。請 Agent 開一個 Markdown 檔，把剛才的討論寫進去，要走四步。模型先決定檔案放哪裡、叫什麼、寫什麼，必要時先呼叫工具查目錄。接著產生 Markdown 文字並提出「在這個路徑建立檔案」的呼叫，到這一步為止還只是文字與參數。然後執行框架把呼叫交給檔案工具或終端機，底層程式真的在磁碟上寫入。最後工具回傳結果，模型再讀一次，確認檔案存在、內容正確。

所以單獨的模型可以寫出 Markdown 的內容，但不能只靠生成文字在電腦裡建立檔案。四步裡分得出三件事：模型提出動作、工具執行動作、結果得到驗證。做投影片也是同一條路：先寫逐頁稿與程式，執行框架跑程式產出 PPTX，再開檔檢查。能走到哪一步，看當時接了哪些工具、授了哪些權。

**原話與來源**

- 「就連開一個 md 把討論寫進去應該都是 harness 做了一連串的動作才做得到，單純 llm 是做不出這個操作」（09-19 17:51）
- 「提出、執行、驗證 這個應該是不用出現，因為 5 就示範怎麼做了，不用硬套情境」（09-20）

### 7｜六種介入方式

**畫面**

- 主訊息：依 Agent 干預流程的深淺排列。
- 人直接使用工具：1 對話　2 交辦　3 製作工具
- 程式在流程中呼叫：4 結構化判斷　5 流程指派 Agent　6 Agent 管理流程
- 圖：一張六格圖片

**筆記**

圖的任務：六格總覽，兩列三欄，只有編號與名稱，上排是人直接使用工具，下排是程式在流程中呼叫。第 7 到 13 頁可重用此圖逐頁亮一格
版型：總覽

知道它怎麼動之後，下一個問題是它可以站在各位流程的哪個位置。同一件研究想法測試，Agent 可以用六種方式參與。我原本想到三種：人向它請教、它產出程式後退出、直接接入流程節點；攤開之後是六種。前三種是人直接用工具，後三種是程式接 API。

接下來一種一頁，每種用同一套標準看：適合什麼情境、優缺點各是什麼、要交出多少信任與權限、成本與採用難度多高。最後一頁用同一套標準總結。這四件事跟下午評估表是同一組：情境對收益，信任與權限對條件與風險，成本與難度對成本。所以上半場其實是先拿六種用法示範一次評估，下午各位對自己的工作再做一次。

**畫面**

- 主訊息：Agent 只提供建議，流程不變，仍由人執行。
- 適用情境：聊天介面即可，零建置、隨時可用；適合定義未明、規則未定，或成品已有而需要另一個角度檢查；例如詢問這類問題文獻上常用哪些方法、各有什麼限制，拿到建議後自行選擇
- 代價與條件：資料不必開放，但產出是建議而非成品；對話不累積，回答的是通則；諮詢 AI 之前先形成自己的觀點與機關立場
- 圖：承辦人流程 自行查找資料 → 自行判斷 → 自行產出；流程外另有「AI 對話」一格，以「提出問題」「取得建議後自行處理」兩條標籤與流程相連
- 來源：數發部手冊 4.2.17

**筆記**

圖的任務：讓人看出 Agent 與正式流程之間沒有連線，人在兩者之間來回，帶回的只有建議
版型：案例

備註用：2026-09-22 PPTX 版把情境、案例、優缺收成「適用情境」「代價與條件」兩個面板，並加一張承辦人流程與流程外 AI 的圖；六種各頁同此版型。

第一種，對話。人在正式流程之外和它來回，它不碰流程、沒有任何寫入權，回答之後就退出，流程裡沒有它。這是介入最淺的一種。工具是 ChatGPT、Claude 這類聊天介面，不用接任何東西。

情境與案例：研究者問「這類問題文獻上常用哪些方法、各有什麼限制」，拿到建議自己選。適合定義還不清楚、規則還在摸、想聽不同方向的時候；也適合成品已經有了、想多一雙眼睛的時候，例如結論定稿前請它逐句對照結果圖表挑毛病。它在對話裡當什麼角色，後面用幕僚的說法再講。

優點：零建置成本，訂閱就能用，資料不必開給它，風險最低。缺點：給的是建議不是成品，每次對話從頭說一遍，累積不下來；它看不到你的檔案與流程，答的是通則。很多規則是在對話裡摸出來的，所以它是後面幾種的起點，但停在這裡就只是聊天。數發部手冊 4.2.17 講的就是這一種的用法：在諮詢 AI 之前，先形成自己的觀點與機關立場，避免過度依賴；帶著自己的意見去問，不是把問題整個丟給它。

### 10｜交辦

**畫面**

- 主訊息：交出成品後，Agent 退出，不留在後續流程。
- 適用情境：使用 Agent 產品；適合需要一份可檢查的成品，僅做一次，或規則尚未確定而先看初版；例如把論文清單整理成附來源的比較表，或依選定方法產出結果圖表的初稿
- 代價與條件：得到實際檔案，接受或退回的責任線清楚；但重做結果不保證一致；每年須重新交辦與檢查，一致性不由 Agent 保證
- 圖：承辦人流程 準備需求與資料 → 成品檔案 → 檢查與驗收 → 送出／歸檔；流程外一格「Agent」，以「交辦需求與資料」「送入流程」兩條標籤相連

**筆記**

圖的任務：一個有邊界的工作包：人交入目的與材料，包內 Agent 查找、製作、檢查，交出可驗收的檔案後工作包關閉
版型：案例

第二種，交辦。人交辦一件事，Agent 用工具查找、寫檔、驗證，交出檔案就退出。工具是 Claude Code、Codex 這類 Agent，它有終端機、檔案讀寫，能真的把東西做出來。

情境與案例：交辦它「把去年合條件的事件挑出來，算差異，產統計表、分布圖與逐事件 CSV」，它交出三個檔案。適合要一份可檢查的成品、做一次就好，或規則還不確定、先看一版再決定的時候。

優點：真的做出東西，留下的是可審查的檔案，人接受或退回，責任清楚。缺點：每次重做的結果不保證一樣，Agent 有隨機性；明年還要再做就要再交辦一次，既慢又難比對。所以做完一次覺得對了，就往第三種走，把做法固定下來。

### 11｜製作工具

**畫面**

- 主訊息：建置時有 Agent，運行時只有程式。
- 適用情境：以 Agent 寫程式，通稱 vibe coding；適合規則固定、輸入整齊、按月或按年重新執行；例如資料前處理與跑實驗的腳本，完成後換參數、換資料重新執行
- 代價與條件：相同輸入得到相同輸出，可測試、可重複；但規則變動須修改程式，程式無錯不代表結果正確；程式可不逐行閱讀，輸出必須查驗；規則寫進程式之前，人先確認規則本身
- 圖：每次作業 每次的資料 → 以工具處理 → 人確認結果；流程外一格「AI 產生工具（僅一次）」，以「說明規則與格式」「交付工具」兩條標籤相連

**筆記**

圖的任務：兩條時間線：建置時人與 Agent 討論規則並產生程式；運行時只有資料進入程式、產出表與圖、人驗收。Agent 只出現在前一條
版型：對比

第三種，製作工具。人跟 Agent 對話把程式寫出來，程式接進流程排程執行，之後 Agent 退出，運行時只有程式。這就是現在說的 vibe coding：用對話把程式寫出來，程式可以不讀，但輸出一定要驗。

情境與案例：方法選定之後，請 Agent 寫好資料前處理與跑實驗的腳本，之後換參數、換資料重跑。適合規則已經固定、輸入整齊、要反覆執行的事。

優點是目前六種裡最實在的：程式可預期，同樣輸入每次同樣輸出，不受 Agent 不確定性影響；可測試，錯誤透過測試修掉，修好就是修好；可重複，寫一次每年跑；而且快，跑程式比每次請 Agent 重做便宜得多。這就是 vibe coding 已經開始改變大眾做法的原因：不會寫程式的人，用對話就能得到一支可以驗證的工具。缺點：規則還在變的時候程式會一直改；程式沒報錯不代表結果對，輸出仍要人驗。數發部手冊 4.4 的資安風險清單有一項專門對這一種：開發者未審查就採用 LLM 建議的套件，不存在的套件名稱可能被做成同名惡意程式。程式可以不逐行讀，但用了哪些套件、從哪裡裝，要看一眼。這一種建置時 Agent 接手很多，運行時完全沒有 Agent，所以它不是「比第二種更進階」，是另一種取捨。一條界線：程式跑的時候如果又去呼叫模型，就不算完全退出。

### 12｜結構化判斷

**畫面**

- 主訊息：答案的格式與範圍由程式先定，模型只在裡面選。
- 適用情境：以 API 接決策模型，程式在固定節點送出問題；模型回傳預先定義的選項、是非、評分或機率，不選工具、不決定下一步；適合選項已知、規則明確、量大且需快速的判斷
- 代價與條件：快速、低成本、行為可控；但只能回答預先定義的問題；判斷品質須先以已知答案驗證，判斷錯誤不會自行察覺
- 圖：承辦人流程 逐筆資料 → AI 逐筆判斷 → 人工抽查例外 → 一致結果與紀錄；流程外一格「人先定義選項與範例」，標籤「標準寫進流程，AI 只能選擇某個答案」

**筆記**

圖的任務：一道窄門：左邊只有狀態與問題能進，右邊只回傳預先定義的欄位，門的前後程式路徑筆直不變
版型：案例

第四種，結構化判斷。既有程式在某一步把輸入送給模型，取回結果，照固定路徑往下走。答案的格式與範圍是程式先定好的：是非、選項、評分或一個欄位，模型不能自由發揮，所以結果是限縮的、確定的。模型不選工具、不決定下一步，所以有模型參與，但不是 Agent。工具是接 API 的決策模型，這幾天很紅的 Jev 就是這個形狀：輸入一段狀態與幾個問題，回傳選項、評分或是非的機率，不生成文字。中心預警管線裡的 P 波拾取與震度預測模型也是同一個形狀，只是那是專用模型，前後都是程式。

情境與案例：腳本逐篇把論文摘要送去判斷「是否相關」，或逐筆把實驗結果送去判斷「是否納入」，模型回選項與信心，腳本照固定路徑往下走。適合選項事先知道、規則說得清楚、量大要快的判斷。

優點：快、便宜，模型不會亂跑，程式控制一切。缺點：只能回答事先定好的問題，需要查資料、看情況選下一步的判斷做不到；判斷的品質要先用已知答案驗過，錯了不會自己發現。這一頁要說的是：不是每個判斷點都需要 Agent。這一種目前還在探索，產品剛出來，做法沒定。

- 「固定節點的一次模型呼叫，也不一定就是能自行選步驟、使用工具的 Agent」（09-19 18:00）

### 14｜流程指派 Agent

**畫面**

- 主訊息：事件觸發後，一段工作交給 Agent 自行處理，產物交回流程。
- 適用情境：以 API 接常駐 Agent，自架或託管；適合需查多個來源、處理例外，下一步無法事先寫成固定路徑；例如新事件資料到達後，自動以既定方法重跑實驗補上結果，異常者標記交研究者
- 代價與條件：無須人力守候，留下可檢查的檔案、紀錄或通知；但運行時有不確定性；須交出資料與操作權限，並設置停止條件
- 圖：承辦人流程 觸發條件 → Agent 取資料處理 → Agent 產出結果 → 人放行／歸檔；標籤「Agent 依 SOP 連續執行，中途無須人力介入」

**筆記**

圖的任務：流程中一段有明確入口與出口的封閉區域：事件把材料交入，Agent 在裡面查資料、用工具、處理例外，只能從指定出口交出產物
版型：案例

第五種，流程指派 Agent。事件到達時呼叫 Agent，它自己查資料、選工具、迭代，交出結果給下一節點或人。工具是接 API 的常駐 Agent，像之前講的龍蝦那類：事件觸發，Agent 自己跑迴圈用工具，做完回報。這一類現在有自架的（自己的電腦跑 Gateway）與託管的（廠商的雲端電腦跑）兩種，形狀一樣，差在誰管那台電腦與帳號。

情境與案例：新事件資料到達後，Agent 自己用既定方法重跑實驗，把結果補進圖表，標出異常交研究者。適合資料來了要查幾個來源、視情況選下一步、要留可檢查產物的段。

優點：不用人守著，事件一到就處理，留下的是可檢查的產物。缺點：運行時有 Agent 的不確定性，每次做法可能不同；資料與帳號要開給它，託管版更是交給第三方，對機關是條件問題；要另外決定寫入權限，只讀、只建草稿、還是核准後才寫入。這裡有兩條官方的線：數發部手冊 4.3.6，不在公開或 API 串接的生成式 AI 服務中提供個資與機密資料，託管的常駐 Agent 首先撞到的就是這條；手冊 4.4.3，減少授權 AI 做無法回復的動作，例如寄信與修改紀錄，關鍵行為由人檢核執行。所以第五種在機關裡的合理設定是只建草稿或核准後才寫入。這一種目前在探索階段，可以小範圍試，有人看著。

### 16｜Agent 管理流程

**畫面**

- 主訊息：主 Agent 承接整件工作，於核准點暫停待確認。
- 適用情境：以 API 接多 Agent 編排；適合跨多個系統、途中有核准與交接、完成後需追蹤；例如從找文獻、跑實驗、產圖到寫報告，由 Agent 串接，選方法與結論由人核准

第六種，Agent 管理流程。主 Agent 依回饋選下一步，分派子 Agent 與工具，跨系統查找、建待辦，在核准點停下等人，追蹤到結案。工具是多 Agent 編排，主 Agent 帶幾個子 Agent，是更進階的東西。

### 17｜總結：取捨與現況

**畫面**

- 主訊息：干預越深，信任、權限、成本與難度越高；現階段效益最明確的是製作工具。

**筆記**

六種看完，回到整張圖，用同一套標準總結：情境、優缺、信任與權限、成本與難度。第一，方向：從 1 到 6，交給 Agent 的信任逐步增加，Agent 越可信，用法會慢慢往後走；但每往後一格，成本與採用的技術難度也上升，所以是取捨，不是能力等級。

第二，現況：以現在的技術與大家的經驗，最有收益的是第三種，讓 Agent 寫程式。程式可預期、可測試、可重複、快，vibe coding 已經在改變大眾做法。第四到六種把模型放進運行中的流程，都還在探索，產品在變、做法在變，還沒形成共識。不是不能試，是要知道自己在試什麼：小範圍、可回復、有人看著。也不必把所有事換成 Agent 才算跟上時代；換的理由來自真的用了之後看到的差異，不來自別人的分享。網路上這類產品的示範案例多數是為了示範，看的時候問一句：拿掉 Agent，這件事還會不會做。

第三，信任不只是感覺，有官方的線。行政院 2023 年的參考指引：產出由承辦人做最終判斷，機密文書禁用，不得輸入應保密與個資。數發部手冊 4.2.9：機關作為使用者，對 AI 輔助日常工作的輸出承擔責任並做必要檢查。4.4.3：減少授權 AI 做無法回復的動作，寄信、修改紀錄這類關鍵行為由人檢核執行。2.2：AI 適合介入的條件是有足夠資料、重複性任務、複雜決策邏輯，避免為導入 AI 而 AI，先小規模概念驗證，既有非 AI 方案能解決的不必硬上。國科會 2026 年對 AI Agent 的廉政風險提醒也是同一方向：二次查證、多層驗證、誠實揭露，優先使用機關內的封閉系統。把這些放回六格圖：越往右，越容易碰到無法回復的動作與資料外流，這就是信任要用權限與核准點來換的原因。

**畫面**

**筆記**

### 19｜先畫責任線

**畫面**

- 主訊息：當責者必為人；負責執行、被諮詢、被告知可以交付。

- 當責對應公文的決行：誰決行，誰就對輸出負責
- 工作單「誰驗收」一欄即此；無法填寫的環節，不適合交付
- 圖：同一條八站流程線，決行站標「當責：人」

**筆記**

圖的任務：第 14 頁的流程線，決行一站加標「當責」，其餘不變
版型：流程

派角色之前先畫一條線。管理上有一組四個字：誰負責執行、誰當責、誰被諮詢、誰被告知。Agent 可以負責執行，這是它多數時候的位置；可以被諮詢，就是對話裡請它給方向或挑毛病；可以被告知，就是做完通知一聲，也可以反過來由它通知人。它不能當責。出了事誰負責、誰簽字，永遠是人。這一格對應公文的決行，數發部手冊 4.2.9 說機關對 AI 輔助工作的輸出承擔責任，講的就是這一格。

### 20｜沿流程派角色

**畫面**

- 主訊息：一站一角色，權限隨站而定。
- 備料、會辦、審核只讀；擬稿、歸檔寫入；執行站可執行程式；追蹤站可發送通知。給的權限不超過該站所需
- 同一個 Agent 換站即換角色，換角色即換一段指示；審核自己擬的稿，須另開乾淨的對話
- 圖：同一條八站流程線，每站下方標角色：整理者、討論者、起草者、操作員、審查者、人、記錄者、協調者

**筆記**

圖的任務：第 14 頁的流程線，每站下方標角色；只讀的站淺色，寫入與執行的站深色，決行另一色
版型：流程

沿著流程一站一站派。備料是整理者，查找、擷取、比對，把東西排成可以比較的樣子。會辦是討論者與對手，帶著自己的意見去問，請它列選項附利弊，或者反過來請它找反例、質疑立場；也可以請它扮民眾或記者提問，演練說明。擬稿是起草者，交出可修改的草稿或程式。執行是操作員，跑程式、操作軟體、回讀輸出確認真的做了。審核是審查者，對照標準逐項檢查。歸檔是記錄者，留下決定、理由、未解的問題，這是最容易被忽略、對知識工作最有用的一站，因為它會自己整理，過去對話式做不到。追蹤是協調者，分派、在核准點停下、追到結案，這就是第六種運行時的樣子。

三條規則。第一，權限跟著站走：備料、會辦、審核只讀；擬稿要寫檔；執行要能跑程式；追蹤要能通知。給它的權限不超過那一站需要的，這和六種介入方式那條軸講的信任是同一件事。第二，同一個 Agent 換站就換角色，換角色就是換一段指示，不是要開八個 Agent，換個稱呼也不保證品質提高。第三，審核那一站可以查它自己在擬稿那站寫的東西，條件是換一段乾淨的對話，不要在同一段裡自己審自己。

每一站交出來的東西，人在哪裡看、看什麼，先寫下來：對照表要能逐列查來源，草稿要能改，執行結果要能重跑比對，檢查表要一項一項有結論。這就是下半場要講的完成證據與中間節點。

**原話與來源**

- 「一開始 agent 會扮演討論者，還有派出去搜集資料整理的，還有會議記錄者，跟審視想法提問的等等，那後面階段還有去操控加工機器的，沒有這個具體的語意，全部都被包成一個 agent，這樣一般人就很難想像到底可以怎麼運用」（09-18 13:52）

### 22｜套回案例：一件工作用幾種

回到開頭那件事，把六種套上去。研究想法測試的六個活動：找文獻，交辦 Agent 整理成附來源的清單是第二種，逐篇判斷相不相關可以交決策節點，是第四種；選方法，用第一種問選項，決定由人；寫程式，方法定了就請 Agent 寫成腳本，是第三種；跑資料，腳本反覆執行是第三種，新資料到達自動重跑是第五種；分析，交辦產出結果圖表與初稿是第二種，結論由人下；寫報告，交辦草稿是第二種，定稿由人。要問的方法與限制，一開始是第一種。

所以六種不是選一種，是一件工作的不同段各用不同種。以現況來說，這件事最實在的收益在寫程式與跑資料那兩個活動，也就是第三種；找文獻的相關性判斷與跑資料的自動重跑是可以試、但還在探索的段。下午各位拆自己的工作，做的就是這一頁：先畫出幾個活動，再決定每一個用哪一種，規則說得清楚的先想第三種，真的需要運行時有模型參與，再往後看。分類針對當下這件工作的實際執行方式，不針對產品。
