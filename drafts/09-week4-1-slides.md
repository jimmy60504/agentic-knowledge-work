### 2｜課程目的

**畫面**

- 下午：各自選一件工作，判斷 Agent 可以接手哪一段、是否值得試
- 上半場：Agent 怎麼動、能站在流程的哪裡、每一種值不值得用；下半場：一段工作怎麼做、別人怎麼用

**筆記**

今天的主軸是幫各位整理一下，目前自己的業務有沒有可以用 Agent 幫忙的地方。下午的工作坊，各位拿一件自己的工作出來，看 Agent 可以接手哪一段、值不值得試。要能判斷這件事，先要知道 Agent 拿到一句話之後中間做了什麼，才變成一份表、一支程式或一封信。所以上半場先把這個過程攤開：它怎麼動、能站在流程的哪裡，然後每一種用法都用同一套標準評估一次：適合什麼情境、優缺點、要交出多少信任與權限、成本與難度多高。下半場再看別人怎麼用、自己的業務翻成同樣的語意之後對不對得上、一段工作怎麼做。

今天不是要說中心該導入什麼系統，也不是說哪個科的工作可以自動化。

### 3｜示範：拆解一件工作

**畫面**

- 以年度預警成效統計為例：每年年初，把去年規模 5 以上、深度 40 公里內的地震挑出來，算預警第一報的時效與誤差，做成表與圖進年報
- 圖：橫式五格流程圖，自繪（mermaid）。讀取（挑事件、取第一報與地震報告）→ 計算（報時差、震央距離差、規模差，分陸上海域）→ 確認（納入、取哪一報、異常解釋）→ 產出（統計表、分布圖、年報段落，送審）→ 保存（規則、事件清單、腳本回存）。確認與產出兩格標人的圖示；手上的材料（地震目錄、報次紀錄、去年的表）畫在讀取格上方，成品（年報的表與圖）畫在產出格下方

**筆記**

這一頁在示範怎麼把一件現有的工作拆開。看一件工作，先問四件事：手上有什麼、要交出什麼、中間要判斷什麼、分成幾步。這張圖把四件事都畫出來了：材料在左上，成品在右下，中間五步，其中確認與產出兩步是人要做決定的地方。

案例是年度預警成效統計。每年年初，承辦同仁要把去年規模 5 以上、深度 40 公里內的地震挑出來，逐件算預警第一報的時效、震央誤差、規模誤差，分陸上與海域，做成表與分布圖放進年報。手上有地震目錄、各事件的預警報次紀錄、去年的表。要決定哪些事件納入、多報次的事件取哪一報、異常的數字怎麼解釋。最後表要能重算，年報段落要過審。

這個案例會一路用到底，後面每講一段就回來指這張圖的某一格。下午各位對自己的工作做同一件事。案例依中心同仁公開演講投影片第 22 頁的年度統計表設計，實際作業細節沒有向同仁確認，是依公開資料設計的流程。

### 4｜模型與執行框架

**畫面**

- 左：單獨的模型，只產生文字。寫出計算的程式碼，數字還沒有算出來
- 右：接上執行框架，事情才發生
- 圖：左右兩張圖，自繪。左圖模型方塊，輸出只有一張寫著文字的紙，旁邊的滑鼠與檔案是灰的、沒有連線；右圖同一個模型方塊接上執行框架，往下接終端機、程式、API、瀏覽器四個工具圖示，箭頭從工具回到模型形成循環

**筆記**

先看左圖。模型本身只產生文字，產生的可能是一段回答，也可能是一段動作描述：一行指令、一段程式碼、一個寫明工具名稱與參數的呼叫。它沒有手，寫出計算的程式碼，數字還沒有算出來。

再看右圖。真的讓事情發生的是執行框架。執行框架事先接好可用的工具與執行規則：終端機、程式、API、瀏覽器、滑鼠。模型提出一個工具呼叫，執行框架檢查權限，交給對應的程式執行，把結果送回模型；模型讀到結果決定下一步，繼續操作、請人確認，或交付成果。整個過程是一個循環：人給目標，模型提出動作，工具執行，結果回來，模型再提出下一個動作。

**原話與來源**

- 「一開始先講說他就是用文字的方式，去控制可能像 harness 預先寫好的程式，terminal 或是滑鼠等等，去做到他想做的事情」（09-19 17:49）
- 「4 跟 5 感覺可以合併變成左右比較的兩張圖」「寫出『寄信』不等於寄出 我覺得這個太生硬了」（09-20）
- 來源：[Anthropic〈Building effective agents〉](https://www.anthropic.com/engineering/building-effective-agents)的 augmented LLM 與 agent loop；[OpenClaw〈Agent loop〉文件](https://docs.openclaw.ai/concepts/agent-loop)

### 5｜最小例子：建立檔案

**畫面**

1. 模型決定位置、名稱、內容，必要時先查目錄
2. 產生 Markdown 文字，提出「建立檔案」的呼叫。仍只是文字與參數
3. 執行框架交給檔案工具，程式寫入磁碟
4. 工具回傳，模型再讀一次確認

- 圖：課程 repo 實際請 Agent 建檔的終端機截圖，看得到工具呼叫與回讀那兩步

**筆記**

用最小的例子走一遍。請 Agent 開一個 Markdown 檔，把剛才的討論寫進去，要走四步。模型先決定檔案放哪裡、叫什麼、寫什麼，必要時先呼叫工具查目錄。接著產生 Markdown 文字並提出「在這個路徑建立檔案」的呼叫，到這一步為止還只是文字與參數。然後執行框架把呼叫交給檔案工具或終端機，底層程式真的在磁碟上寫入。最後工具回傳結果，模型再讀一次，確認檔案存在、內容正確。

所以單獨的模型可以寫出 Markdown 的內容，但不能只靠生成文字在電腦裡建立檔案。四步裡分得出三件事：模型提出動作、工具執行動作、結果得到驗證。做投影片也是同一條路：先寫逐頁稿與程式，執行框架跑程式產出 PPTX，再開檔檢查。能走到哪一步，看當時接了哪些工具、授了哪些權。

**原話與來源**

- 「就連開一個 md 把討論寫進去應該都是 harness 做了一連串的動作才做得到，單純 llm 是做不出這個操作」（09-19 17:51）
- 「提出、執行、驗證 這個應該是不用出現，因為 5 就示範怎麼做了，不用硬套情境」（09-20）

### 6｜六種介入方式

**畫面**

- 1 請教　2 一次性交付　3 建置工具後退出
- 4 固定節點呼叫一次模型　5 流程節點呼叫 Agent　6 協調跨節點工作
- 每一種看四件事：情境、優缺、信任與權限、成本與難度
- 圖：六格示意圖（兩列三欄），自繪。每格一個小圖加一行名稱，不加說明文字。圖做好後取代上面兩行。第 7 到 13 頁共用這張圖，逐頁亮一格或加標註

**圖規格**

| 格 | 名稱 | 圖裡畫什麼 |
|---|---|---|
| 1 | 請教 | 人與對話框來回；流程在旁邊，兩者之間沒有連線 |
| 2 | 一次性交付 | 人交辦 → Agent 用工具查找、寫檔、驗證 → 交出檔案 → Agent 退出（虛線） |
| 3 | 建置工具後退出 | 人與 Agent 對話寫出程式 → 程式接進流程排程執行 → Agent 退出（虛線）；運行時只有程式 |
| 4 | 固定節點呼叫一次模型 | 流程節點 → 送狀態與問題 → 模型回選項與機率 → 節點照固定路徑走；模型不碰工具 |
| 5 | 流程節點呼叫 Agent | 事件觸發 → Agent 迴圈（模型與工具往返）→ 產物交下一節點或人 |
| 6 | 協調跨節點工作 | 主 Agent 分派子 Agent 與工具 → 在核准點停下等人 → 追蹤到結案 |

**筆記**

知道它怎麼動之後，下一個問題是它可以站在各位流程的哪個位置。同一件年度成效統計，Agent 可以用六種方式參與。我原本想到三種：人向它請教、它產出程式後退出、直接接入流程節點；攤開之後是六種。前三種是人直接用工具，後三種是程式接 API。

接下來一種一頁，每種用同一套標準看：適合什麼情境、優缺點各是什麼、要交出多少信任與權限、成本與採用難度多高。最後一頁用同一套標準總結。這四件事跟下午評估表是同一組：情境對收益，信任與權限對條件與風險，成本與難度對成本。所以上半場其實是先拿六種用法示範一次評估，下午各位對自己的工作再做一次。

**原話與來源**

- 「目前應該有幾種 agent 的用法，就是直接接入 agent 到節點上做一些處理，還有 agent 產出程式碼，然後 agent 就不介入後面的結果，還有 agent 只是給人建議，並沒有進到整個流程中」（09-19 17:58）
- 「這個感覺比較像是 agent 接手介入程度的感覺」（09-19 18:01）
- 「搞不好我 6 種介入方式就是詳細多講幾張，每個都單獨介紹一下」「上半場應該會有一個一開始開頭把這些方法放進去的一個評估」（09-21）

### 7｜請教

**畫面**

- 情境：定義還不清楚、規則還在摸，想聽不同做法
- 優：零建置、隨時用；缺：給的是建議不是成品，每次從頭說
- 圖：同第 6 頁的六格圖，亮第一格，其餘淡出；格上標籤「對話式」

**筆記**

第一種，請教。人在正式流程之外發問，Agent 回答之後退出，流程裡沒有它。工具是 ChatGPT、Claude 這類聊天介面，不用接任何東西。

情境與案例：承辦同仁問「時效與誤差通常怎麼定義，往年怎麼算，有沒有別的機關的做法」，拿到建議自己算。適合定義還不清楚、規則還在摸、想聽不同方向的時候。

優點：零建置成本，訂閱就能用，資料不必開給它，風險最低。缺點：給的是建議不是成品，每次對話從頭說一遍，累積不下來；它看不到你的檔案與流程，答的是通則。很多規則是在請教裡摸出來的，所以它是後面幾種的起點，但停在這裡就只是聊天。數發部手冊 4.2.17 講的就是這一種的用法：在諮詢 AI 之前，先形成自己的觀點與機關立場，避免過度依賴；帶著自己的意見去問，不是把問題整個丟給它。

**原話與來源**

- 「agent 只是給人建議，並沒有進到整個流程中」（09-19 17:58）
- 「第一個可以用對話式」（09-20）
- 來源：[[moda-public-sector-ai-playbook]] 4.2.17

### 8｜一次性交付

**畫面**

- 情境：要一份可檢查的成品，做一次就好，或先看一版再說
- 優：真的做出東西、可審查；缺：每次重做不保證一樣，明年還要再交辦
- 圖：亮第二格；標籤「Agent」

**筆記**

第二種，一次性交付。人交辦一件事，Agent 用工具查找、寫檔、驗證，交出檔案就退出。工具是 Claude Code、Codex 這類 Agent，它有終端機、檔案讀寫，能真的把東西做出來。

情境與案例：交辦它「把去年合條件的事件挑出來，算差異，產統計表、分布圖與逐事件 CSV」，它交出三個檔案。適合要一份可檢查的成品、做一次就好，或規則還不確定、先看一版再決定的時候。

優點：真的做出東西，留下的是可審查的檔案，人接受或退回，責任清楚。缺點：每次重做的結果不保證一樣，Agent 有隨機性；明年還要再做就要再交辦一次，既慢又難比對。所以做完一次覺得對了，就往第三種走，把做法固定下來。

**原話與來源**

- 「第二個跟第三個用 agent」（09-20）

### 9｜建置工具後退出

**畫面**

- 情境：規則已固定、輸入整齊，每年每月要重跑
- 優：可預期、可測試、可重複、快；缺：規則還在變時程式跟著改，輸出仍要人驗
- 圖：亮第三格；標籤「Agent，vibe coding」

**筆記**

第三種，建置工具後退出。人跟 Agent 對話把程式寫出來，程式接進流程排程執行，之後 Agent 退出，運行時只有程式。這就是現在說的 vibe coding：用對話把程式寫出來，程式可以不讀，但輸出一定要驗。

情境與案例：規則確定之後，請 Agent 寫好篩選事件與計算誤差的腳本，之後每年重跑。適合規則已經固定、輸入整齊、每年每月要重做的事。

優點是目前六種裡最實在的：程式可預期，同樣輸入每次同樣輸出，不受 Agent 不確定性影響；可測試，錯誤透過測試修掉，修好就是修好；可重複，寫一次每年跑；而且快，跑程式比每次請 Agent 重做便宜得多。這就是 vibe coding 已經開始改變大眾做法的原因：不會寫程式的人，用對話就能得到一支可以驗證的工具。缺點：規則還在變的時候程式會一直改；程式沒報錯不代表結果對，輸出仍要人驗。數發部手冊 4.4 的資安風險清單有一項專門對這一種：開發者未審查就採用 LLM 建議的套件，不存在的套件名稱可能被做成同名惡意程式。程式可以不逐行讀，但用了哪些套件、從哪裡裝，要看一眼。這一種建置時 Agent 接手很多，運行時完全沒有 Agent，所以它不是「比第二種更進階」，是另一種取捨。一條界線：程式跑的時候如果又去呼叫模型，就不算完全退出。

**原話與來源**

- 「建置工具後退出 這個就是 vibe coding」（09-20）
- 「目前版本最有收益的會是 agent 寫程式，因為程式本身是可以預期的，不會受到 agent 的不確定性影響，只要透過測試來把程式碼的錯誤修掉，而且可以重複使用，速度又快」（09-21）
- 「程式若在運行時又呼叫模型，就不算 Agent 寫完後完全退出」（09-19 18:00）
- 來源：[[vibe-coding]]；[[moda-public-sector-ai-playbook]] 4.4 風險清單

### 10｜固定節點呼叫一次模型

**畫面**

- 情境：選項已知、規則說得清楚、量大要快的判斷
- 優：快、便宜、不會亂跑；缺：只能答事先定好的問題，判斷品質要先驗
- 圖：亮第四格；標籤「API，決策模型」

**筆記**

第四種，固定節點呼叫一次模型。既有程式在某一步把輸入送給模型，取回結果，照固定路徑往下走。模型不選工具、不決定下一步，所以有模型參與，但不是 Agent。工具是接 API 的決策模型，這幾天很紅的 Jev 就是這個形狀：輸入一段狀態與幾個問題，回傳選項、評分或是非的機率，不生成文字。中心預警管線裡的 P 波拾取與震度預測模型也是同一個形狀，只是那是專用模型，前後都是程式。

情境與案例：腳本把每件事件送去判斷「是否納入」「多報次取哪一報」，模型回選項與信心，腳本照固定路徑算下去。適合選項事先知道、規則說得清楚、量大要快的判斷。

優點：快、便宜，模型不會亂跑，程式控制一切。缺點：只能回答事先定好的問題，需要查資料、看情況選下一步的判斷做不到；判斷的品質要先用已知答案驗過，錯了不會自己發現。這一頁要說的是：不是每個判斷點都需要 Agent。這一種目前還在探索，產品剛出來，做法沒定。

**原話與來源**

- 「第四個很像現在這幾天流行的 jev」（09-20）
- 「固定節點的一次模型呼叫，也不一定就是能自行選步驟、使用工具的 Agent」（09-19 18:00）
- 來源：[[jev-system-one-decision-model]]；[[cwa-eew-2024-hualien-case-study]] 第 43 到 45 頁

### 11｜流程節點呼叫 Agent

**畫面**

- 情境：事件到了，要查幾個來源、視情況選下一步的那一段
- 優：不用人守著、留可檢查的產物；缺：運行時有不確定性，資料與權限要交出去
- 圖：亮第五格；標籤「API，常駐 Agent」

**筆記**

第五種，流程節點呼叫 Agent。事件到達時呼叫 Agent，它自己查資料、選工具、迭代，交出結果給下一節點或人。工具是接 API 的常駐 Agent，像之前講的龍蝦那類：事件觸發，Agent 自己跑迴圈用工具，做完回報。這一類現在有自架的（自己的電腦跑 Gateway）與託管的（廠商的雲端電腦跑）兩種，形狀一樣，差在誰管那台電腦與帳號。

情境與案例：每次規模 5 以上的事件結束後，Agent 自己取報次與地震報告，算差異補一列到年度表，標出異常交承辦。適合事件來了要查幾個來源、視情況選下一步、要留可檢查產物的段。

優點：不用人守著，事件一到就處理，留下的是可檢查的產物。缺點：運行時有 Agent 的不確定性，每次做法可能不同；資料與帳號要開給它，託管版更是交給第三方，對機關是條件問題；要另外決定寫入權限，只讀、只建草稿、還是核准後才寫入。這裡有兩條官方的線：數發部手冊 4.3.6，不在公開或 API 串接的生成式 AI 服務中提供個資與機密資料，託管的常駐 Agent 首先撞到的就是這條；手冊 4.4.3，減少授權 AI 做無法回復的動作，例如寄信與修改紀錄，關鍵行為由人檢核執行。所以第五種在機關裡的合理設定是只建草稿或核准後才寫入。這一種目前在探索階段，可以小範圍試，有人看著。

**原話與來源**

- 「直接接入 agent 到節點上做一些處理」（09-19 17:58）
- 「第五個比較像之前的龍蝦」（09-20）
- 來源：[[openclaw-how-people-use-it]]（自架）；[[grok-bot-hosted-agents]]（託管）；[[moda-public-sector-ai-playbook]] 4.3.6、4.4.3

### 12｜協調跨節點工作

**畫面**

- 情境：整段跨好幾個系統、中間有核准點、做完要追蹤
- 優：整件事有人接手到底；缺：出錯回不到哪裡，權限、紀錄、回復都要先做好
- 圖：亮第六格；標籤「API，多 Agent 編排」

**筆記**

第六種，協調跨節點工作。主 Agent 依回饋選下一步，分派子 Agent 與工具，跨系統查找、建待辦，在核准點停下等人，追蹤到結案。工具是多 Agent 編排，主 Agent 帶幾個子 Agent，是更進階的東西。

情境與案例：從逐事件補列、年底彙整、產圖表、寫年報段落、送審到依審核意見修改，整段由 Agent 串接，定稿由人核准。適合整段跨好幾個系統、中間有核准點、做完還要追蹤的事。

優點：整件事有東西接手到底，人只在核准點出現。缺點：一步錯後面全錯，出錯時不知道回到哪裡；權限、錯誤處理、紀錄與回復都要先做好，成本最高；沒有前面幾種的經驗就直接上這一種，等於在不熟的流程上放最不確定的東西。這一種目前離大眾做法最遠。

**原話與來源**

- 「第六個就是更進階的東西」（09-20）
- 來源：[Anthropic〈Building effective agents〉](https://www.anthropic.com/engineering/building-effective-agents)的 orchestrator-workers；[LangGraph](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)

### 13｜總結：取捨與現況

**畫面**

- 信任遞增；成本與採用難度同時上升；目前最划算的是第三種
- 數發部手冊：無法回復的動作由人檢核執行；先小規模驗證；非 AI 能解的不硬上
- 圖：同第 6 頁的六格圖，下方一支由 1 指向 6 的箭頭標「交給 Agent 的信任」，另一支標「成本、採用的技術難度」；第三格亮起標「已在改變大眾做法」，第四到六格標「探索中」

**筆記**

六種看完，回到整張圖，用同一套標準總結：情境、優缺、信任與權限、成本與難度。第一，方向：從 1 到 6，交給 Agent 的信任逐步增加，Agent 越可信，用法會慢慢往後走；但每往後一格，成本與採用的技術難度也上升，所以是取捨，不是能力等級。

第二，現況：以現在的技術與大家的經驗，最有收益的是第三種，讓 Agent 寫程式。程式可預期、可測試、可重複、快，vibe coding 已經在改變大眾做法。第四到六種把模型放進運行中的流程，都還在探索，產品在變、做法在變，還沒形成共識。不是不能試，是要知道自己在試什麼：小範圍、可回復、有人看著。

第三，信任不只是感覺，有官方的線。行政院 2023 年的參考指引：產出由承辦人做最終判斷，機密文書禁用，不得輸入應保密與個資。數發部手冊 4.2.9：機關作為使用者，對 AI 輔助日常工作的輸出承擔責任並做必要檢查。4.4.3：減少授權 AI 做無法回復的動作，寄信、修改紀錄這類關鍵行為由人檢核執行。2.2：AI 適合介入的條件是有足夠資料、重複性任務、複雜決策邏輯，避免為導入 AI 而 AI，先小規模概念驗證，既有非 AI 方案能解決的不必硬上。國科會 2026 年對 AI Agent 的廉政風險提醒也是同一方向：二次查證、多層驗證、誠實揭露，優先使用機關內的封閉系統。把這些放回六格圖：越往右，越容易碰到無法回復的動作與資料外流，這就是信任要用權限與核准點來換的原因。

**原話與來源**

- 「六種介入我自己覺得也跟信任程度有關……但也是會牽涉到成本跟採用技術的困難度等」（09-20）
- 「目前版本最有收益的會是 agent 寫程式……介入更深的目前都還在探索階段，還沒有像 vibe coding 已經開始轉變大眾觀點」（09-21）
- 「每一個方式都會秀一下使用情境跟案例，然後去分析該方法的優缺點，最後在總結」「信任本身也是要帶一下那個數發部公布的指引」（09-21）
- 來源：[[moda-public-sector-ai-playbook]] 2.2、4.2.9、4.4.3；[[public-sector-ai-adoption-barriers-and-examples]] 行政院 2023 指引、國科會 2026 Agent 風險提醒；原文 [數發部手冊 PDF](https://www-api.moda.gov.tw/File/Get/moda/zh-tw/WwHCroVhwWy52dw)

### 14｜套回案例：一件工作用幾種

**畫面**

- 一件工作的不同段各用不同種；規則說得清楚的先想第三種
- 圖：同第 3 頁的五格流程圖，每格標上介入方式的號碼：讀取「2 或 5」、計算「3」、確認「人；是否納入可交 4」、產出「2，表圖與段落」、保存「3，規則進腳本」；人負責的格用人的圖示

**筆記**

回到開頭那件事，把六種套上去。年度成效統計的五格：讀取，第一年交辦 Agent 挑事件、取報次是第二種，之後每次事件結束自動補一列是第五種；計算，規則固定後寫成腳本每年跑，是第三種；確認，哪些事件納入、多報次取哪一報，由承辦判斷，其中「是否納入」這種選項已知的判斷可以交決策節點，是第四種，但決定權還在人；產出，統計表、分布圖與年報段落草稿交辦 Agent 產出，是第二種，年報定稿由人核准；保存，規則與事件清單回存，腳本是第三種留下的東西。要問的定義、往年做法，一開始是第一種。

所以六種不是選一種，是一件工作的不同段各用不同種。以現況來說，這件事最實在的收益在計算與保存那兩格，也就是第三種；讀取的自動補列與確認的決策節點是可以試、但還在探索的段。下午各位拆自己的工作，做的就是這一頁：先攤開幾格，再決定每一格用哪一種，規則說得清楚的先想第三種，真的需要運行時有模型參與，再往後看。分類針對當下這件工作的實際執行方式，不針對產品。

**原話與來源**

- 「應該說一開始有個年報的範例，結尾是不是要套看看」（09-21）
- 「六種介入我自己覺得也跟信任程度有關」（09-20）
