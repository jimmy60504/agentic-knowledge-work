# 第五週草稿：導入 AI 之前先規劃

> 狀態：供討論的初稿，尚未放入正式教材。2026-09-27 使用者重訂主線並要求先不展開：「現在真的要來導入 AI，但是如果沒有規劃就直接導入，常常效果不好，變成做做樣子」；「太想導入 AI，不適合導入的東西也導入，變成多此一舉」。

> 前一版的講義五份、講師參考書單、Story 圖兩小節與示範題細節，暫存於 commit `b2eb425`，主線確認後再依需要取回。

## 主線

署內開始實際導入 AI。導入時常見兩種失敗：

1. **未經規劃便導入。** 不清楚要解決什麼問題、怎樣才算成功，做完也無法說明效果，最後流於形式。
2. **為導入而導入。** 不適合的工作也交給 AI，檢查與修正的成本超過原本的做法，反而多此一舉。

因此本週先找出業務中真正的痛點，再判斷每個痛點是否適合交給 AI。

## 本週的結構

本週以討論為主，分為前後兩段（使用者 2026-09-27 定）：

1. **前段：提供討論框架。** 以他人導入 AI 的經驗說明兩種失敗的成因，歸納成討論時要回答的幾個問題。
2. **後段：工作坊當場討論。** 學員依框架討論自己的業務，找出痛點，並判斷是否適合交給 AI。產出為一份「導入前規劃」，取代原本的痛點卡（使用者 2026-09-27 定）。

## 前段：兩種賦能與兩種失敗

Agent 賦能個人有兩種方式（使用者 2026-09-27 提出，例子為使用者原話整理）：

| | 以前做不到，現在能做 | 以前沒時間做，現在有時間做 |
|---|---|---|
| 軟體團隊的例子 | PM 以前不會寫程式，現在可以寫簡單的小工具 | RD 以前沒時間做 CI/CD 與測試，現在終於有時間把事情做好 |
| 署內可能的對應 | 預報員或研究人員不寫程式，但清楚需求，可以自行製作資料整理或繪圖的小工具 | 資訊或維運同仁有時間補齊測試、文件與監控 |
| 合適的原因 | 清楚要什麼、看得出結果對不對，缺的只是操作；工具自用，做錯代價低 | 省下的時間用於把原本的工作做好；測試與監控本身就是檢查機制 |
| 反面版本 | 不懂業務的人用 Agent 做出看似完整的分析，卻無法判斷對錯 → 多此一舉 | 省下的時間拿去接更多工作，品質沒有改善，或做出沒人使用的東西 → 流於形式、工作加密 |

兩種賦能各有對應的失敗：做不到的事，要問自己是否看得出結果對錯；沒時間做的事，要問做出來給誰用、省下的時間用在哪裡。這兩個問題接到後段的導入前規劃。依據見[賦能筆記](../kb/arguments/ai-enablement-what-changed.md)第五節。

## 導入前規劃（候選，六項）

依[失敗案例](../kb/arguments/ai-adoption-failure-cases.md)與[賦能研究](../kb/arguments/ai-enablement-what-changed.md)反推出四項，再與[既有導入框架比對](../kb/tools/ai-pre-adoption-plan-frameworks.md)補上替代做法、資料與權限、受影響者：

1. 具體問題與範圍：一件實際發生、會重複發生的事，從哪一步到哪一步。
2. 現行做法的基準：現在怎麼做、花多久、多常出錯。
3. 替代做法：調整流程、一般程式或暫不處理是否更合適。
4. 資料與權限：資料能否取得、能否放進 AI（個資、保密等級）。
5. 檢查分工與做錯代價：誰檢查、要花多久、影響到誰、能否還原；檢查的人能從中得到什麼（例如退件理由寫成規則後，Agent 下次不再犯；看過更多案例，對工作更有把握）。
6. 成功與停止條件：由做事的人自己判斷怎樣算成功、試多久、何時停止、省下的時間用在哪裡；結果作為自己的回饋，不交給上級考核。

測量整段流程含檢查的時間、下游與審核者的時間、錯誤與退回、實測與感受的差異，不以使用率或件數當作成效。測量結果是給做事的人自己看的回饋，不作為考核指標；成為指標後，人會朝指標調整而偏離原本目的（使用者 2026-09-27）。
