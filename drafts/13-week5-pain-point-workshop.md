## 本週的目的

第四週讓學員知道 Agent 可以參與哪些環節，並用 Domain Storytelling 畫出一件工作的現況。第五週回到前一步：先確認哪些地方真的需要解決，再決定用什麼方法處理。處理方法包括調整流程、撰寫一般程式、以 vibe coding 快速試作、正式規劃設計，或暫不處理；使用 AI 只是其中幾種。

第四週的現況圖在本週用作標記痛點的底圖，也說明為何選用這種方法：圖讓人與 Agent 對工作的理解一致，並能從圖上選出一段，逐步補成規格。

學員在課堂上完成痛點卡，講師收回彙整，作為第六週之後依需求排課的依據。QC 與資料庫重整是否為優先的痛點，也在本週確認。

### 現況圖的作用

第四週選用 Domain Storytelling，是因為文字難以讓人與 Agent 對同一件工作取得共識。只寫「協助整理研究資料」，看不出資料從哪裡來、誰負責整理、結果交給誰，以及哪一步需要人判斷。Story 圖把這些關係放在同一個畫面：演員執行活動，使用或產生工作物件，再交給下一位演員。參與者沿著編號活動逐句確認，便能找出彼此理解不同之處。[Domain Storytelling 入門指南](https://domainstorytelling.org/quick-start-guide)

這也對應 DDD（領域驅動設計）的基本想法：開發者需要理解業務使用的詞語與規則，並在討論、圖和程式中維持一致的說法。撰寫程式的人可能換成 Agent，領域專家更需要檢查 Agent 是否理解工作的方式。[Domain Storytelling 與 DDD](https://domainstorytelling.org/domain-driven-design)

過去自行繪製 Story 圖，須逐一拖拉圖形、安排版面，佔用討論業務的時間。現在可以先口述一次具體案例，請 Agent 整理成活動句並產生圖，人只需逐句確認活動是否發生、物件名稱是否正確、交接是否遺漏。

在本週，現況圖是標記痛點的底圖。等待、重做與交接遺失多半出現在箭頭之間；某支箭頭接不上下一支，通常表示中間缺少資料或判斷。痛點標在圖上的位置，也決定後續改善的範圍。

### 從痛點卡到規格

一整件工作通常太大，無法直接交給 Agent 實作。落在四格表右側、需要正式規劃的痛點，先沿著圖選出起點與終點清楚的一段。例如研究流程可以只選「研究者提出研究問題 → 檢索文獻 → 形成論文清單 → 研究者檢查」，暫不納入選定研究方法與撰寫報告。

選出這一段後，在圖上討論哪支箭頭適合由 Agent 執行、它需要讀取什麼、應留下什麼結果供人檢查，以及人在哪裡核准或退回。現況圖與加入 Agent 的第二版圖並列，便能看見改動的範圍。

規格再補上每一段的輸入、輸出、完成條件與例外情況。以文獻檢索為例，圖上寫「Agent 整理論文清單」，規格還要說明清單包含哪些欄位、如何保留來源、找不到資料時如何回報，以及由誰決定清單能否用於下一步。痛點卡的「怎樣算解決」與「如何驗證」兩欄，即是規格中完成條件的起點。程式中的名稱沿用已確認的業務語言，人便能從圖找到規格，再從規格找到對應的程式行為。[從故事形成需求](https://domainstorytelling.org/requirements)

整條路徑可以反覆修正：口述一次工作 → 畫出現況 → 標記痛點 → 選出一段 → 討論 Agent 如何介入 → 補足規格 → 實作並檢查。本週完成到標記痛點與決定做法；後續步驟依痛點卡的彙整結果，排入第六週之後的課程。

## 示範（30 分）

講師選一件自己實際經歷的工作，照學員實作的順序走完一次，讓學員看到每一步要留下什麼。

**候選示範題：備課時投影片用語被反覆退回。** 這是本課程備課過程中實際發生、且有紀錄的問題，可以完整走完所有步驟。

| 步驟 | 示範內容 |
|---|---|
| 事件回溯 | 投影片畫面多次被指出口語，每次要逐頁重改，同樣的修正重複出現 |
| 標記浪費 | 重做；交接遺失（標準只存在講師腦中，Agent 看不到） |
| 追原因 | 用語標準沒有寫下來，每次對話都要重新說明 |
| 痛點卡 | 頻率：每份投影片數次；代價：每次重改數十分鐘；替代做法：口頭提醒 |
| 四格表 | 容易驗證、代價低；處理方式是調整流程：把標準寫成一份規則檔，每次先讀 |

接著用同一張四格表快速比較一個高風險例子：讓 Agent 直接判定 QC 是否通過。這件事不易驗證，因為錯誤的資料被放行後看起來仍然正常；代價也高，因為目錄會被長期引用。它應該正式規劃，或只讓 Agent 列出疑點、由人判定。兩個例子並列，學員可以看出同樣是 AI 協助，做法完全不同。

若講師另有更貼近署內業務的例子，可替換示範題；另一個備選是公開資料中的年報地震數不一致（113 年年報 2,181 與 2,180），但只能示範查核與提問，不能推論署內實際流程。

## 實作（120 分）

依業務分組，例如 QC 組、資料庫組，以及其他業務組。同組的人工作相近，回想時可以互相提醒。

| 步驟 | 時間 | 做法 | 留下什麼 |
|---|---|---|---|
| 1. 翻閱紀錄 | 10 分 | 各自打開最近兩週的行事曆、寄件備份與最近修改的檔案，記下三件卡住、等待或重做的事 | 三則事件摘要 |
| 2. 兩人互訪 | 25 分 | 兩人一組，用事件回溯問題互相追問細節，由對方代為記錄 | 每則事件的經過、時間與處理方式 |
| 3. 標記痛點 | 30 分 | 同組合併事件，放上現況圖或活動清單，標出浪費類型與替代做法 | 標記後的流程 |
| 4. 追原因與排序 | 25 分 | 從症狀追到原因；依頻率與每次代價排序 | 排序後的痛點清單 |
| 5. 痛點卡與分流 | 20 分 | 選出前兩項寫成痛點卡，放入四格表，決定做法 | 兩張痛點卡 |
| 6. 交流 | 10 分 | 各組用一分鐘說明最優先的痛點與決定的做法 | 無 |

現況圖不必完整。第四週已畫過圖的學員可以沿用；沒有圖的組別，列出活動順序即可。Agent 可以協助整理訪談紀錄、分類事件、提出原因的候選，但哪些痛點是真的、哪些值得處理，由學員決定。

課後不需繳交作業。痛點卡由講師收回。

## 講義

### 講義一：事件回溯問題

不問「有什麼困擾」，請對方描述一件最近發生的具體事件。

- 最近一次發生是什麼時候？當時在做什麼？
- 怎麼發現的？
- 誰處理？花了多久？
- 最後怎麼解決？之後有沒有再發生？
- 如果對方談到解法（例如「需要一個新系統」），接著問：有了之後，哪件事會不一樣？現在沒有的時候怎麼處理？

QC 與資料庫可加問：

| QC | 資料庫重整 |
|---|---|
| 最近一次被擋下的資料是什麼？為什麼被擋？ | 最近一次查不到或查錯資料是什麼情況？ |
| 哪一條規則最常需要人判斷？依據是什麼？ | 最常查的三個問題是什麼？現在要花多久？ |
| 新人多久才能獨立處理？常錯在哪裡？ | 同一數字在不同地方不一致時，以哪一個為準？ |
| 結果交給誰？對方如何使用？ | 資料修訂後需要通知誰？有沒有遺漏過？ |

### 講義二：知識工作的浪費類型

改寫自豐田生產方式的浪費分類；改寫為知識工作版本是 agent 的整理，非原始分類。

| 類型 | 在知識工作中的樣子 |
|---|---|
| 等待 | 等核准、等資料、等回覆 |
| 重做 | 被退回、數字錯誤需重算 |
| 搬運 | 複製貼上、轉換格式、重新輸入 |
| 查找 | 找舊檔、找版本、找知道答案的人 |
| 交接遺失 | 資訊傳到下一站時遺漏 |
| 過度處理 | 無人閱讀的報表、重複的檢查 |
| 知識集中 | 只有某一個人會做；可問：這個人請假一週會如何？ |

另外記下替代做法：自製的 Excel、對照表、便利貼與私人筆記。每一份替代做法都表示正式流程在該處有缺口。

### 講義三：從症狀追到原因

依序提問，不在第一個原因就停下：

1. 這件事造成什麼錯誤或耗時？
2. 原因在哪一個上下游環節？能否更早發現？
3. 目前有沒有預防機制？為什麼沒有發揮作用？

排序依兩個問題：多久發生一次、每次要付出多少代價。只發生一次但印象深刻的事件，先確認是否為個案。

### 講義四：痛點卡

| 欄位 | 填寫內容 |
|---|---|
| 具體事件 | 至少一則實際發生的事件，作為證據 |
| 頻率與代價 | 多久發生一次；每次花費的時間或造成的影響 |
| 影響對象 | 哪些人或單位受影響 |
| 目前的替代做法 | 現在如何應付 |
| 原因假設 | 追問後認為的原因 |
| 怎樣算解決 | 可以觀察或檢查的完成條件 |
| 如何驗證 | 做出來之後，怎麼判斷結果正確 |
| 失敗代價 | 做錯時影響多大 |
| 能否還原 | 做錯時能否回到原狀 |
| 決定的做法 | 調整流程、一般程式、vibe coding、AI 產出人核准、正式規劃設計，或暫不處理 |

### 講義五：驗證難度與失敗代價

| | 失敗代價低 | 失敗代價高 |
|---|---|---|
| **容易驗證** | 直接以 vibe coding 或 AI 完成。例：報告圖表、個人查詢工具 | AI 產出，人核准後才使用。例：對外文稿、季報草稿 |
| **不易驗證** | 小範圍試用、抽查，結果只供參考。例：大量文件摘要、內部整理 | 正式規劃設計，或不用 AI。例：QC 自動判定、資料庫遷移、測報系統 |

另外檢查三件事：

- 錯誤會不會被發現：沒有人察覺的錯誤最危險。
- 能否還原：可以重做的工作，風險較低。
- 影響範圍：自己使用、單位內部，或對外發布、被其他系統引用。

驗證難度可以降低。先準備一組已知答案的測試資料，或讓新舊做法並行比對，同一件工作就會移向容易驗證的一側。高風險的工作，先回答「如何驗證」，再決定是否交給 AI。

同一個主題依交出的範圍不同，位置也不同：讓 Agent 列出 QC 疑點屬於容易驗證；讓它直接判定通過與否則屬於右下角。資料庫遷移本身屬於右下角，但比對新舊欄位、產生差異報告可以交給 AI。

## 講師參考

以下供備課使用，不放入學員講義。

### 需求工程的五個觀念

1. 需求需要挖掘：熟練的工作已成習慣，提出者常直接說解法，而且只看得到自己那一段。
2. 區分問題與解法：Zave 與 Jackson 將需求（R，世界應成立的狀況）、領域知識（D，世界本來的運作方式）與規格（S，系統的行為）分開；許多失敗來自 D 的假設錯誤。Agent 降低了撰寫 S 的成本，R 與 D 仍須由懂業務的人說清楚。
3. 需求是協商後的共識：利害關係人的需求會衝突，需求文件記錄的是決定。
4. 需求必須可驗證：每條需求附判斷標準（Volere 的 fit criterion），對應第四週的「完成證據」。
5. 需求會改變：需要能追溯來源與影響範圍。

### 軟體工程借自其他領域的概念

Scrum 名稱出自 Takeuchi 與 Nonaka 1986 年分析產品開發團隊的文章；Kanban 與 Lean 來自豐田生產方式；設計模式來自建築師 Christopher Alexander；迭代開發對應 PDCA；需求工程源自國防與航太的系統工程；checklist 來自航空業；事後檢討來自醫學與飛航安全。除 Scrum 與 B-17 之外，出處多為常見說法，放入教材前須查證。
