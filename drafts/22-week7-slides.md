### 4｜補齊漏洞

**畫面**

- 主訊息：要補齊漏洞，定位與檢查必須一起考慮

- 圖：`assets/week6-diagrams/w6-36-upstream.png`｜錯誤在定位時產生，流到檢查端才被發現

**筆記**

- 口述：這一點承接第六週的長期方向：在上游補上防呆。因此預檢與定位軟體的翻新，視為同一個整體的兩個部分。

### 6｜規則自成一塊

**畫面**

- 版面：圖為主
- 主訊息：規則只有一份，兩端依賴規則，彼此以檔案相接
- 圖：`assets/week7-diagrams/w7-06-dependency.png`｜定位端與檢查端都指向檢查程式（規則庫），兩端之間以波形檔與定位結果檔相接，共用資料夾在下方

**筆記**

- 口述：規則若在兩端各寫一份，遲早會不一致；兩端若互相呼叫，任何一端翻新都會牽動另一端。規則不依賴兩端，兩端依賴規則：預檢先用它在送出前把關，翻新後的定位軟體再用它在挑波時攔截。檔案格式本來就是現行流程的介面，舊的定位軟體存出的檔案，新的檢查程式也能直接檢查。目前規則先與檢查端放在同一個專案，之後獨立。

**原話與來源**

- 原話：「應該說檢查程式本身是自己一塊，然後挑波跟 qc 各自去調用」（10/17）；「規則不依賴 qc 跟 pick，是 qc 跟 pick 依賴這個規則，只是目前專案還不大先這樣打包而已」（10/17）；「兩邊的程式碼要能夠獨立運作，只靠［波形檔］［定位結果檔］等檔案傳遞訊息」（10/17）

### 7｜投影片為骨架

**畫面**

- 版面：圖為主
- 主訊息：以投影片為線索，把原本的流程全部走一遍
- 段落：照訓練投影片的步驟，逐一查看整個流程跑過哪些人工檢查與程式檢查，記下每一步讀了什麼、怎麼判斷、門檻多少。
- 圖：`assets/week7-diagrams/w7-07-slide-walkthrough.png`｜投影片的三大步驟，標出每一步是人工檢查還是程式檢查

**筆記**

- 口述：預檢負責的是第一步的後半與整個第二步，原本在送出之後才做的檢查，提前到送出之前執行；第三步的入庫維持原本的做法。
- 口述：清單照投影片原有的步驟編號排列，不另訂新的流程，承辦看到的是熟悉的步驟，只是改由程式先行執行。但投影片只寫出承辦要做的步驟，每個步驟背後的程式對資料做了什麼，投影片並沒有寫。

**原話與來源**

- 原話：「實際上想講的就是依照原本的流程全部走一遍，所以我們用投影片當作線索，去看整個流程到底跑過哪些人工與程式檢查」（10/20）；「一開始根據 qc 的投影片作為主體，照著上面的流程把整個步驟都列出來」（10/19）

### 8｜分階段替換

**畫面**

- 主訊息：要分階段替換原本的程式，必須先保持行為一致
- 段落：每換掉一支程式，新的程式都要與原本的行為相同，否則同一筆資料經過新舊流程會得到不同的結果，也說不出差異從哪裡來。因此替換之前，要先查清每個步驟對定位結果檔的每一項改變。
- 圖：`assets/week7-diagrams/w7-08-same-result.png`｜同一筆資料經過新舊流程，結果必須相同

**筆記**

- 口述：要查清的是每個步驟讀取哪些欄位、依什麼條件判斷、門檻是多少、結果如何處理。

**原話與來源**

- 原話：「我們要階段性的去替換原本的程式，我們為了要先保持行為的一致性，才會要把整個流程對［定位結果檔］的改變都調查清楚」（10/19）

### 9｜查到程式的層次

**畫面**

- 主訊息：查到程式的層次，以實際行為為準
- 版面：圖為主
- 段落：重構或重寫之前，先把舊程式實際的行為保存下來，作為之後比對的標準。軟體工程稱這種做法為特性測試（characterization test）。
- 圖：`assets/week7-diagrams/w7-09-program-level.png`｜文件、原始碼、實際執行三層，越往下越接近實際；查到的行為保存下來作為比對的標準

**筆記**

- 口述：有原始碼的程式，Agent 逐支讀取原始碼，與說明文件和程式的介面對照；只有執行檔的，Agent 解析執行檔，在測試機上實際執行、觀察行為。這樣調查出來的，多半是文件沒有寫、卻會影響結果的細節，例如模型的選用方式、測站表如何決定哪些資料留下、程式依賴的執行環境。
- 口述：照文件重寫會漏掉舊程式實際在做的事。文件寫什麼不是標準，舊程式實際怎麼做才是現行的規格，連它的錯誤也先記下來，之後再逐項決定要保留還是修正。調查找到、投影片沒有寫到的操作，掛回最相關的步驟下並註明來源。特性測試一詞出自 Michael Feathers 的《Working Effectively with Legacy Code》（2004），處理的正是接手沒有規格的舊程式又要改寫的情況。逐檔對照原始碼、還要實際執行驗證，所需的人力很大，沒有 Agent 時很難在短時間內完成。具體的發現留待與業務單位開會時對齊，課堂上不展開。

**原話與來源**

- 原話：「簡單來講就是我們重構或重寫前就是要把行為保存下來」（10/20）；「我們用 agent 去調查可以追溯出不只文件上的行為，可以真的回到原始碼來看到底發生了什麼事情，然後只有 exe 的也可以透過 agent 來測試行為來觀察」（10/19）；「要有一個規則的溯源，不然直接照著投影片重寫可能會漏掉東西？」（10/05）

### 10｜補充：逆向工程

**畫面**

- 樣式：補充
- 版面：圖為主
- 主訊息：只有執行檔時，也可以借助逆向工程的工具
- 段落：來源：InfoQ，2026-10-17；專案頁 github.com/morluto/rea（MIT 授權）。開發者尚未實際試用。

### 段｜三、規則與來源的大表

### 11｜回溯到原文

**畫面**

- 主訊息：每一條規則都要能回溯到原文
- 段落：先不寫規則，而是逐項列出每個來源實際做了什麼，記錄原文的位置、條件、門檻與輸出。目前共 18 個來源、672 個條目。
- 段落：條目與規則兩個方向都要有交代：每個條目被規則接住、註明不納入或列為待決定；每條規則有來源，或註明沒有現行依據。程式自動檢查這兩個方向。
- 圖：`assets/week7-shots/w7-12-matrix-year.png`｜規則與來源的大表，依年代排列【待拍】

**筆記**

- 口述：規則要在會議上討論，被問到「這條規則從哪裡來」時，必須能直接指出原文。條目的數量遠多於規則，因為大部分是作業步驟、修正或其他功能。

**原話與來源**

- 原話：「看那些程式到底在哪裡，還有每個程式實際上做了什麼……就是要有一個規則的溯源」（10/05）；「規則來源可以整理成一個超級大的表格嗎？就是每個 row 是檢查的欄位，然後每個 col 是某一個資料來源，然後照時間排」（10/13）

### 13｜列舉與決定

**畫面**

- 主訊息：Agent 負責列舉，人負責決定
- 版面：圖為主
- 段落：來源太多，人一個個讀不完。由人訂定格式、指揮多個 Agent 平行調查；結果有漏掉或讀錯時，回到原文核對，再調查一次；最後由人決定去留。
- 圖：`assets/week7-diagrams/w7-13-agent-survey.png`｜人指揮 Agent 平行調查來源，漏掉或讀錯時再調查一次，最後由人決定去留

**筆記**

- 口述：第一輪由 4 個 sub-agent 平行閱讀 13 個來源，列出約 340 個條目；第一輪依意圖分組，可能漏掉條件，因此第二輪每個來源由一個 Agent 重讀，先不看既有的整理，增為 18 個來源、672 個條目，也找出第一輪讀錯的地方。人訂定擷取的格式與比對的標準，決定不納入的理由與待決定的項目，不一致的數值整理成會議議題交由檢查端決定。
- 口述：這延續第五週的「不自行裁定」。待決定的項目先以一個月的真實資料算出會攔到幾筆，再交給人判斷，Agent 不自行新增規則。重掃也找出第一輪讀錯的條目，都是回到原文核對才確認的。

**原話與來源**

- 原話：「大概是人沒辦法看這麼多規則，那就是指揮 agent 幫忙調查，這過程中還會有要回去調查第二次等等」（10/20）；「開發在梳理規則的時候用了超級大量的 agent 去盤查，而且還需要反覆查閱跟驗證」（10/17）；「前三項先對應，4 到 8 項加成候選規則」（10/05）；「門檻不一致可能可以先做成分級然後拿去討論？」（10/09）

### 14｜依業務邏輯分類

**畫面**

- 圖：`assets/week7-diagrams/w7-14-classify.png`｜九個項目各對應一個地震學上的概念，重跑與入庫分流另列兩組規則

**筆記**

- 口述：分類照業務邏輯，不照來源、舊程式或投影片的步驟：每個項目檢查一個地震學上的概念，例如發震時間、震央、深度、規模、挑波、測站與定位品質。同一個概念的檢查原本散在好幾個來源與步驟裡，依概念分類之後只占一列，負責這個概念的同仁也能直接找到相關的規則。一條規則只檢查一件事、只有一個等級；名稱寫檢查的欄位與判斷，不寫門檻。偵測與處理分開，重跑與入庫分流另列。
- 口述：同一件事常分散在好幾個來源與步驟裡，例如定位誤差大於 2 公里，同時出現在訓練投影片與流程文件中。依來源或步驟分類，同一條規則會散在好幾處。原本「深度為 0 或過淺」放在同一條分兩級，但深度為 0 是流程錯誤、深度很淺是要確認的計算結果，意義不同，因此拆成兩條。

**原話與來源**

- 原話：「依對象分類，應該主要是要講我們分類是照業務邏輯分，也就是檢查某一個地震學上的概念」（10/20）；「我們應該是會要比較認真的去討論這些規則是怎麼建出來，怎麼分類，還有為什麼有這些去留，這個應該在大表上的欄位可以看出這個設計意圖」（10/19）【待補更直接的原話】

### 15｜單一意圖

**畫面**

- 版面：圖為主
- 主訊息：規則要拆到只有一個意圖，與程式的單一職責原則相同
- 圖：`assets/week7-diagrams/w7-15-single-intent.png`｜以深度為例：只做門檻會把兩種原因混在一起，拆成兩條之後各有一種處置

**筆記**

- 口述：原本「深度為 0 或過淺」放在同一條規則，分兩級處理；但深度為 0 代表沒有計算或經人工修改，屬於流程錯誤，深度大於 0 而很淺則是計算過的結果，要確認是否合理。兩件事意義不同，拆成兩條之後，每條規則只有一個意圖、一個等級。這和寫程式的單一職責原則（single responsibility principle）相同：一個單位只負責一件事，名稱說得清楚，修改一處不會牽動另一處，也能單獨測試。
- 口述：如果只是單純把檢查門檻做上去，不同的錯誤原因會混在同一條規則裡，而後面接的處置並不一樣：深度為 0 要重新執行定位計算，不能手動填深度；深度很淺則是確認計算結果是否合理。規則拆到一個意圖，處置才能寫得具體。拆開之後，每一個原因都連到一個地震學上的概念，例如定位計算是否完成、速度模型算出的深度是否合理，這樣才有辦法引導承辦怎麼改善，而不只是告訴他「不合格」。這也呼應前一頁：分類依地震學的概念，原因也落在同一個概念上。
- 口述：大表的欄位同樣圍繞這個原則：每條規則一列，寫出目的、檢查的欄位、建議處置與狀態；說不出單一目的的規則，就是要再拆或拿去討論的。

**原話與來源**

- 原話：「這個原因就是會連到一個地震學的概念，這樣我們才有辦法引導到底怎麼改善」（10/20）；「通常如果只是單純把檢查門檻做上去，那可能會有不同錯的原因混在一起，那我們後面所接的處置就會不一樣」（10/20）；「大表的欄位本身應該不是要講欄位，而是我們規則要拆到只有一個意圖，這個跟寫程式那個單一職責的概念是差不多的」（10/20）

**畫面**

|---|---|

- 原話：「就是我現在整個驗證的 code 目前如果要重新規劃設計成一般軟體工程的測試流程，你要怎麼重新打造？」（10/19）；「我覺得這個感覺就是可以跟實際的 unit test 對應？」（10/19）

- 原話：「那裡面會有一個頁面寫版本號跟更新了什麼主要功能，還有一個更新按鈕跟版本切換的功能」（10/19）；「伺服器版本是不是也要可以切換已經發佈的版本，這樣如果有問題回報，我也可以切回去看？」（10/19）；「到時候規則可能會分 repo，那就是規則自己是獨立自己有設定的」（10/19）

### 段｜結語：AI 在哪些環節協助

### 28｜AI 的位置

**畫面**

- 主訊息：結果要穩定的節點用程式，AI 用在開發端
| 環節 | AI 的工作 | 人的工作 |
|---|---|---|
| 盤查來源 | 平行閱讀原始碼與文件，逐條列出條件 | 訂定格式，決定去留 |
| 查證 | 開發大表與原文檢視的介面 | 點開原文核對，開會定案 |
| 驗證 | 製作錯誤檔、在測試機執行舊程式、逐筆比對 | 判斷差異的歸類 |
| 執行檢查 | 不參與，由程式依規則執行 | 維護規則 |
| 打包與發布 | 打包腳本與發布流程、實測安裝與更新 | 決定公開範圍與交付管道 |

**筆記**

- 口述：檢查節點的輸入與輸出都是可以預期的結構化資料，以程式執行結果穩定、能追溯，一個月約一千筆幾秒即可完成。AI 的投入集中在開發端，每天執行的檢查交給穩定而便宜的程式。

**原話與來源**

- 原話：「我們會選用一般程式規則而不是 agent rag 也是這樣比較穩定且成本低，而且輸入輸出都是可以預期的結構化資料，所以才沒有把節點搞成一個 agent，但是開發在梳理規則的時候用了超級大量的 agent 去盤查」（10/17）
