## 要解決的問題

資料處理承辦為了達到件數，常有步驟未執行或僅抽選部分事件處理。目錄維護端檢查出問題只能退件，雙方反覆往返。目標是讓大部分問題在資料處理端送出之前就被發現或修正，目錄維護端收到的資料只剩少數需要討論的事件。

## 攔截的三層

使用者的整理：先假設所有步驟都出錯，看原本的流程有多少錯誤沒有被攔截、流到下一位承辦身上。這些錯誤分成三層處理，前兩層由程式負責，最後沒被攔截的才需要人看。

1. **流程錯誤：以規則攔截。** 步驟沒有執行或格式不對，例如存檔後未重跑 HYPO、header 出現 24 時、權重不在 0 至 4 與 9 之內。這類錯誤有明確的對錯，程式可以直接攔截或修正。
2. **執行品質：以物理限制篩選。** 挑波等判斷沒有標準答案，但結果必須符合物理上的合理範圍，例如殘差、定位誤差、深度與規模。Sb-A-3 列出的大量檢查條件，實際上就是這一層的限制。
3. **其餘項目：由人檢視。** 通過前兩層、仍需看波形才能判斷的事件，例如疑似重複事件、有感遠震是否入庫。

### 現況：全部出錯時的攔截位置

以[資料處理端完整步驟](16-earthquake-qc-current-state.md)的 18 步為準，假設每一步都出錯：

| 錯誤 | 層 | 現行攔截位置 |
|---|---|---|
| No Event 的 A file 未確認就刪除或保留 | 流程 | 無 |
| 存檔後未重跑 HYPO（相位順序錯、規模為 0 或 0.01） | 流程 | CheckPfile，於目錄維護端 |
| header 出現 24 時、60 秒 | 流程 | CheckPfile，於目錄維護端 |
| 權重不在 0 至 4 與 9 之內 | 流程 | 無（投影片：無法檢查） |
| 新測站未加入 HYPO3D.sta、站名有空白 | 流程 | 無 |
| 在 GPS 狀態 0 的測站點了 P 或 S | 流程 | 無 |
| 殘差過大 | 品質 | CheckPfile，於目錄維護端 |
| ERH、ERZ 為 0 或大於 2 | 品質 | CheckPfile，於目錄維護端 |
| 深度小於 0 | 品質 | CheckPfile，於目錄維護端 |
| 規模小於 0 | 品質 | CheckPfile，於目錄維護端 |
| 近站未 picking、GAP 大於 160 度 | 品質 | 部分（CheckPfile 的 ???）；GAP 無 |
| 測站數或相位數不足、超出監測範圍 | 品質 | CheckPfile 與篩選，於目錄維護端 |
| 發震時間相近的疑似重複事件 | 人工 | Samp.exe 與目視，於目錄維護端 |
| 有感遠震是否入庫 | 人工 | 目錄維護端詢問 |

現行的檢查程式大多已經存在，只是全部在目錄維護端執行；資料處理端沒有任何一道攔截，所以全部出錯時，每一項都會流到目錄維護承辦身上。另有五項流程錯誤目前完全沒有攔截。

### 物理限制的候選

除投影片已列的殘差、誤差、深度與規模之外，以下是 agent 提出、可以補進第二層的候選，需向目錄維護端確認是否合理：

- S 波到時晚於 P 波到時。
- 到時隨震央距離增加，順序明顯顛倒者列出。
- S-P 時間與震央距離的比例符合一般的 Vp/Vs 範圍（和達圖）。
- 人工 picking 與速度模型 1 的理論到時相差過大者列出（EventPick 的 Show Theory 已有此計算）。
- 各測站的視規模分散過大者列出。

## 初步構想

### 使用情境

資料處理承辦完成一日的定位之後、送交目錄維護端之前，對當日目錄執行一次程式。程式修正能以規則處理的問題，嘗試重跑定位，並列出必須回到 UI 處理的事件。承辦處理完人工項目再送出，檢查報告隨資料一併交給目錄維護端。

### 處理流程

```text
當日 P file
  → 1. 掃描：讀取 header 與相位，執行全部檢查
  → 2. 自動修正：時間進位、遠震欄位字元等規則明確的項目
  → 3. 自動重跑：誤差或規模異常者，以不同模型重新定位並比較
  → 4. 判定去向：入庫、不入庫、刪除、需詢問
  → 5. 產出報告：已修正、已重跑、待人工處理、去向統計
  → 承辦處理人工項目 → 重新執行 → 人工項目清零後送出
```

### 畫面：任務清單

使用者的想像：Agent 以一份任務清單追蹤當日的處理進度，分開顯示 Agent 已經完成的工作與目前需要承辦協助的地方。承辦只需處理「需要協助」的項目，處理完後 Agent 接續執行，直到清單全部完成。任務清單同時就是交給目錄維護端的檢查報告。

以下為示意，事件編號與內容皆為虛構：

```text
當日 QC 任務清單                          完成 9 / 14，需要協助 3

已完成（Agent）
  [v] 掃描 42 筆 P file，列出 7 項錯誤
  [v] 事件 A：header 時間 24:00:03 修正為次日 00:00:03
  [v] 事件 B：未算規模，重跑 HYPO 後 ML 2.1
  [v] 事件 C：ERH 2.8，改用 1D 模型後 ERH 1.2（兩次結果並列供比對）
  [v] 事件 D：規模小於 0，標示刪除
  [v] Samp.exe 比對完成，疑似重複 1 組
  ...

需要協助（承辦）
  [ ] 事件 E：S 波殘差 6.2 秒，請在 EventPick 重新 picking
  [ ] 事件 F、G：發震時間相差 0.6 秒，請比對波形確認是否重複
  [ ] 事件 H：遠震且列為有感，請確認是否入庫

等待中
  [ ] 重新掃描，確認錯誤清單清空
  [ ] 送交目錄維護端
```

每一筆「已完成」都附上修改前後的內容，承辦與目錄維護端可以抽查；承辦在「需要協助」處理完一項後，Agent 自動重新檢查該事件，確認通過才移到「已完成」。

### 設計原則

- **第一版只用指令執行，不操作 UI。** 命令列程式與資料檔（CheckPfile 等檢查程式、P file 的讀寫）由程式直接處理；必須在 EventPick 等圖形介面完成的步驟，一律列為提示，由承辦操作。UI 自動化暫不嘗試。
- **只修改規則明確的欄位。** 程式修改 header 與重跑定位，不修改 picking；需要看波形的問題一律列為人工項目。
- **每一筆修改都留紀錄。** 保留原始檔，報告列出修改前後的內容，目錄維護端可以據此抽查。
- **門檻集中在一份設定檔。** 重複事件秒差、殘差、誤差等數值目前各處不一致，由目錄維護端訂定一次，上下游共用同一份。
- **沿用現有檢查邏輯。** 以 CheckPfile 的檢查項目為基礎，補上現行程式無法檢查的項目（權重、測站檔、GAP），不另起一套標準。

### 分階段導入

| 階段 | 範圍 | 目的 |
|---|---|---|
| 一 | 只掃描與產出報告，不修改任何檔案 | 以過去的退件資料驗證，確認程式抓得到目錄維護端實際退件的問題 |
| 二 | 加入自動修正 | 時間進位等規則明確的項目不再退件 |
| 三 | 加入自動重跑 | 以 HYPO 的 Fortran 原始碼編譯獨立的命令列版本，驗證與 EventPick 內的結果一致後使用 |
| 四 | 設為送出條件 | 人工項目未清零不得送出，需上下游與主管同意 |

第一階段不修改資料，風險最低，也最容易取得雙方同意，適合作為明天提出的起點。

### 自動重跑：編譯 HYPO 並驗證一致性

使用者指出 HYPO 應有 Fortran 原始碼，可以單獨編譯成命令列程式，不必透過 EventPick 的介面。做法如下：

1. **取得原始碼與設定。** 包含 HYPO 本體、速度模型檔、測站檔（HYPO3D.sta）與控制參數，並確認 EventPick 實際呼叫的是哪一個版本。
2. **編譯成獨立程式。** 以 gfortran 編譯；舊式 Fortran 可能需要相容選項。同一份原始碼可在 Windows 與 Mac、Linux 上編譯，開發與測試不受限於承辦的電腦。
3. **驗證行為一致。** 取一批過去已定位完成的事件，分別以新編譯的程式與 EventPick 內的 HYPO 定位，逐筆比對發震時間、經緯度、深度、ERH、ERZ 與規模。編譯器不同可能造成浮點數的微小差異，因此比對以容許誤差判定，差異超出容許範圍的事件逐筆追查原因。
4. **通過後才用於自動重跑。** 驗證用的事件與比對結果保留下來，之後修改程式或更換編譯器時重跑一次，作為回歸測試。

## 訪談問題

1. 最常退件的原因是哪些？是否有退件紀錄可以提供，作為第一階段驗證的資料？
2. 重複事件的秒差門檻以哪一個為準（投影片 1 秒、紙本 2 秒、Samp.exe 3 秒）？
3. 哪些 header 修正可以由程式直接修改，哪些必須由人確認？
4. HYPO 的 Fortran 原始碼在哪裡？EventPick 呼叫的是哪個版本、使用哪些速度模型與參數檔？
5. P file 格式是否有規格文件？
6. 資料處理承辦一日的處理流程為何？哪些步驟最常省略，原因是什麼？
