# 第七週 ghost deck：把檢查規則整理成有依據的規則庫

> 狀態：ghost deck 第二版（2026-10-20），供使用者排序與刪減。第一版依做了什麼排成 41 頁，細節多、設計概念不明顯；第二版依[第七週文稿](20-week7-draft.md)第二版的 20 個設計重點重排：每個重點一頁主張，證據較多的重點另加一頁證據，共 30 頁，不另設段落頁，各段第一頁的上方以路線圖標出目前位置。第一版見 git 歷史。
> 依 `skills/ghost-deck-from-own-words.md` 製作：標題以使用者原話為底，只刪贅字、不改用詞；agent 補的頁面標【無原話】。每頁標明類型：主張（設計重點）、證據（案例的細節）、補充。
> 原話來源：本課的備課對話與檢查端的開發對話（完整抽出見 `tmp/week7-user-messages.md`、`tmp/week7-user-messages-0102-0110.md`，不進 git）。日期為台灣時間。依去識別化規定，系統、程式與文件名稱以［］內的一般說法取代。
> 講述約 60 分鐘，之後為討論與交換意見。畫面：「開發截圖」指講師保存的截圖（見文稿「附：可用的截圖」，需以虛構資料重拍或遮蔽）；自繪圖標【待畫】。

## 概念串接

1. 上週做出原型，本週把原型背後的檢查規則認真整理出來；原型沒有丟棄。
2. 一、要補齊漏洞，定位與檢查必須一起考慮；規則只有一份，兩端依賴規則，以檔案相接。
3. 二、清單以投影片為骨架；要分階段替換，先保持行為一致；所以查到程式的層次。
4. 三、每條規則都能回溯到原文；Agent 列舉、人決定；依檢查對象分類；從不同角度看把關；去留依原則。
5. 四、每一環都能檢查；規則只寫在一處；新舊一致、差異歸類；以測試守住。
6. 五、環境能重現；處理留下紀錄；能安裝也能退回；只公開可以公開的。
7. 結語：結果要穩定的節點用程式，AI 用在開發端；交給 AI 的工作要準備查證的方式。

### 4. 要補齊漏洞，就要一起考慮

- 類型：主張

- 原話：「很多東西會漏到 qc 這邊，是因為［定位軟體］那個程式本身流程設計沒有阻擋這些問題，變成所有的像是［舊檢查程式］都是要人為自己去點才會觸發，那我們整個流程要把洞補齊就是要一起考慮」（10/19）；「qc 一些漏洞會需要前面 picking 來補」（10/06）

- 備註：只在送出前檢查，可以減少退回，卻無法讓錯誤不再產生。

### 5. 證據：兩份程式包中間有個共用的資料夾

- 類型：證據
- 標題：兩個程式包中間有個核心共用的資料夾

- 備註：測站表、速度模型與定位計算程式決定了定位結果，共用資料夾本身就是規格的一部分。

### 6. 規則只有一份，兩端依賴規則

- 備註：規則若在兩端各寫一份，遲早不一致；預檢先用它在送出前把關，翻新後的定位軟體再用它在挑波時攔截。

## 二、從投影片到每個步驟的實際行為

### 7. 清單以投影片為骨架

- 類型：主張
- 標題：根據 QC 的投影片作為主體，照著上面的流程把整個步驟都列出來

### 8. 要分階段替換，先保持行為一致

- 類型：主張

### 9. 查到程式的層次

- 類型：主張

## 四、證據鏈與測試

### 21. 每一個環節都要能檢查

- 類型：主張
- 標題：要能夠證明現在流程跟之前的一樣
- 原話：「現在應該是要先把規則都整理驗證，你有什麼驗證的方案嗎？就是要能夠證明現在流程跟之前的一樣」（10/09）
- 畫面：路線圖標出第四段；四個環節：原文 → 條目 → 規則 → 程式 → 結果，各標檢查方式【待畫】。
- 備註：任何一條規則被質疑時，都能回答出處、理由與是否和舊程式一致。

### 22. 規則只寫在一處

- 類型：主張
- 標題：規則要變成 single source，才不會有一大堆散落各地的版本
- 原話：「規則要變成 single source，才不會有一大堆散落各地的版本，這樣整理後也可以很清楚的放在 UI 上面說明到底在檢查什麼」（10/02）
- 畫面：同一份規則檔產生說明頁、大表、門檻圖與測試【待畫】。
- 備註：門檻的方向與等級也寫進規則檔，界線測試由它自動產生。

### 23. 新舊結果要一致，差異一律歸類

- 類型：主張
- 標題：一個是我們重建的規則有正常運作，另一個是原本程式測出來的結果符合我們所理解的門檻值
- 原話：「要區分一個是我們重建的規則有正常運作，另一個是原本程式測出來的結果符合我們所理解的門檻值，那例子可以變成門檻兩邊的例子，然後例子旁邊打勾是有過上面兩個測試的結果？」（10/19）
- 畫面：門檻例子與兩項測試的打勾（開發截圖）。
- 備註：一個月 1,049 個檔案與 74 個錯誤檔逐筆比對；差異歸入四類；比對也抓到 Agent 讀錯原始碼的錯誤。

### 24. 以測試守住證據鏈

- 類型：主張
- 標題：驗證的 code 重新規劃成一般軟體工程的測試流程
- 原話：「就是我現在整個驗證的 code 目前如果要重新規劃設計成一般軟體工程的測試流程，你要怎麼重新打造？」（10/19）；「我覺得這個感覺就是可以跟實際的 unit test 對應？」（10/19）
- 畫面：兩張小表：依失敗的意思分層、依資源分級（三級）。
- 備註：缺少資源時測試失敗而不是略過；持續更新的測站表改以虛構的版本測試行為。

- 類型：主張
- 標題：人工按下修正後，就會有更改紀錄
- 原話：「自動修正可以變成像是［定位計算程式］重跑那樣，就是人工去按那個修正後，就會有更改紀錄？」（10/19）；「一個是就是確認過他是對的，那另一個就是這個事件他覺得要回報，然後回報的文字是必填」（10/19）；「qc 如果拿到回報他也會需要標記是有問題的事件」（10/19）
- 畫面：預覽修正、提示確認、QC 端確認與退回（開發截圖）。

### 27. 能夠安裝，也能退回

- 類型：主張
- 標題：一個頁面寫版本號跟更新了什麼，還有更新跟版本切換
- 原話：「那裡面會有一個頁面寫版本號跟更新了什麼主要功能，還有一個更新按鈕跟版本切換的功能」（10/19）；「伺服器版本是不是也要可以切換已經發佈的版本，這樣如果有問題回報，我也可以切回去看？」（10/19）；「到時候規則可能會分 repo，那就是規則自己是獨立自己有設定的」（10/19）
- 畫面：版本頁與設定頁【待截】。
- 備註：免安裝，解壓即用，同一個壓縮檔兼作更新套件；共用資料夾不打包，由設定指定位置；只接受本機連線；舊版保留可切回；規則與程式各自有版本，啟動時檢查相容性。

### 28. 只公開可以公開的內容

- 類型：主張
- 標題：先只公開版本資訊，這樣比較不會有風險
- 原話：「有辦法做成可以線上檢查更新嗎？然後就是用 ghpage 去做發布？」「好，先照 B 做，這樣也比較不會有風險」（10/19；B 為只公開版本資訊）
- 畫面：發布流程：推上版本標籤 → 測試與打包 → 只發布版本資訊，套件另行交付【待畫】。

## 結語

### 29. 節點用程式，AI 用在開發端

- 類型：主張
- 標題：沒有把節點搞成一個 Agent，但梳理規則時用了大量的 Agent
- 原話：「我們會選用一般程式規則而不是 agent rag 也是這樣比較穩定且成本低，而且輸入輸出都是可以預期的結構化資料，所以才沒有把節點搞成一個 agent，但是開發在梳理規則的時候用了超級大量的 agent 去盤查」（10/17）
- 畫面：AI 與人的分工表（盤查來源、查證、驗證、執行檢查、打包與發布）。

### 30. 交給 AI 的工作，要準備查證的方式

- 類型：主張
