## 整體架構

本週要把設計方向都講到，細節只用來佐證方向可行，可以依討論取捨。時間比較充裕，不固定各段的長度，可以邊講邊討論。系統仍在開發中，部分功能尚未完成。第二、三段為本週重點。

| 段落 | 設計方向 |
|---|---|
| 一、合併的理由 | 從流程上解決 QC 的問題，減少後面真正需要 QC 的項目 |
| 二、資料與介面 | 資料都存在專案資料庫，只在邊界轉換格式 |
| 三、畫面 | 模組化、逐步導入改變、即時回饋、以任務列表正向引導並主動協助 |
| 四、接上現行流程 | 每一段都能單獨接上，分階段替換 |

| 六、開發的時間成本 | Agent 降低寫程式的成本，設計要經由迭代才能符合組織實際的運作，仍然很花時間 |
| 下一步 | 互動式教學與自動挑波 |

## 一、合併的理由

**方向：從流程上解決 QC 的問題，減少後面真正需要 QC 的項目。** 第七週的結論是錯誤在定位時產生，定位與檢查必須一起考慮。上週課後向業務單位展示，決定把切事件、挑波與檢查合併成一個系統。

現行流程（示意圖 `arch-before.png`）每一步讀取上一步寫出的檔案，被 QC 退件時要回到挑波程式修改、重新定位，追查修改只能比對各階段的檔案。合併之後有四個做法：

- 從根本消除格式類的錯誤。佐證：事件要依時間排序，但定位到很遠的地震時，發震時間會變早，順序因此顛倒。現在輸出時才依發震時間排序並產生檔名。
- 挑波時即時輔助。佐證：任務列表當場提示，不必在兩支程式之間往返（第三段）。
- 留下 QC 判斷的依據。佐證：最近的測站沒有挑選，可能是沒有資料。挑波時從波形看得出來，這項資訊可以記錄下來。測站品質篩選依平直、缺漏、雜訊等情況判斷，標準無法達到時至少有個根據。
- 規則仍只有一份，各模組直接引用（回扣第七週「規則只寫在一處」）。

## 二、資料與介面（本週重點）

**方向：資料都存在專案資料庫，只在邊界轉換格式。** 各程式獨立演化，彼此以檔案交接，格式難以更改。沿用數十年之後，已無法應付現在的需求，例如無法記錄歷史、精度受到限制。

### 內部：專案資料庫

想法來自反射震測處理系統與其他類似的地震分析軟體，這些系統都以專案為中心，資料與處理都在專案內進行。各模組共用同一個專案資料庫（示意圖 `arch-after.png`）。

佐證：

- 資料依 QuakeML 的概念拆成事件、定位解、挑選、到時的關聯與規模。
- 每次定位都保留一版定位解，每一次輸入與輸出都記成一筆工作，因此可以記錄歷史。
- 波形只建索引，原檔留在外部（連續波形檔一天約 43 GB）。
- 工作的單位是事件，事件有自己的狀態，進度與交付以工作日計算。

### 對外：只在邊界轉換

- 檔案格式：對接現有系統時才輸出相位檔，做法接近向下相容。未來若要改用更現代、更通用的格式，只需增加一種輸出，不必重新撰寫系統。
- 定位程式：介面傳遞定位本身的內容，不再限定相位檔。每一種定位程式各寫一個轉接，日後可以試用較新的定位程式。

## 三、畫面（本週重點，搭配示範）

### 模組化

**方向：每個模組對應原本的一個步驟，以資料庫串接，日後容易增加新功能。**

佐證：

- 切地震對應切事件程式，定地震對應挑波與定位程式，QC 對應檢查程式。
- 每個模組是獨立的頁面，單螢幕時為分頁，多螢幕時各放一個螢幕。
- 原本以為需要獨立的「波形目錄」，試做之後改為切地震的時間軸。試做比討論更快看出結構是否合理。

### 導入改變而不干擾使用者

**方向：原有的操作先沿用，新功能與新操作由使用者自己選擇，逐步吸收。**

- 沿用原有的習慣：原本的功能當初設計出來多半有其目的，這些目的不一定寫在程式碼或文件中。若未沿用，使用者可能找不到原本依賴的資訊，因此重寫之前先向使用者請教用途，尚未確認的先沿用。佐證：測站分頁依位置排列，不同分頁中位置相近的列，對應的測站在地圖上也相近，這是請教使用者才得知的。以排序表查證，同一列的測站距離中位數為 39 至 84 公里，隨機打亂時為 135 至 150 公里。
- 實驗性功能：原本沒有的功能各自設有開關，預設關閉，目前有 14 項。一方面可以測試尚未成熟的功能，一方面降低學習門檻，使用者逐項打開，不會因為一次變化太大而不知道如何使用。大家接受並使用一段時間之後，就併入一般功能。
- 自訂操作方式：開發者的新想法放到設定頁作為選項（例如滾輪的用法），由使用者自行選擇。這樣保有創新的空間，使用者也不會在工作趕時間時受到阻礙。

### 面板連動與即時回饋

**方向：所有資訊都即時更新，操作時累積體感。** 這是介面現代化最大的理由。滑鼠懸停、拖曳或點選時，相關的面板都立即更新。操作的當下就看得到各個數值如何影響最終結果，腦中更容易建立連結。以前的迭代週期要全部跑完，還要自己想辦法畫圖才看得到。

佐證：

- 修改挑選：新增、刪除或修改一筆到時與權重，隨即重新定位，地圖與殘差跟著更新。
- 懸停：滑鼠移到測站選擇的格子上，地圖的資訊欄即顯示這一站的殘差。
- 拖曳：拖曳波形上的到時線時，地圖上由 S−P 換算的距離圓即時更新。
- 點選：在地圖上點選測站，波形列表即跳到這一站所在的分頁。

### 任務列表（本段重點）

業務單位提到，希望有一個在旁邊協助檢查 QC 的程式，這個形式很接近遊戲的任務列表。兩個方向都尚待同仁實際試用確認。

**方向一：QC 由批評與阻擋轉為正向引導。**

佐證：

- 同一條規則，由「錯在哪裡」改寫成「還有哪件事要完成」。剛開始挑波時測站數不足，呈現為尚未完成，不列為錯誤。
- 主線是定出一個可以交付的地震，依挑波的進度逐步出現下一個目標，支線遇到時才出現。
- 選到有任務的測站時，才顯示這一站的任務。點選任務即跳到目標測站，每次定位後即時更新。
- 挑波時不阻擋：存檔只寫入資料庫，性質接近工作階段的暫存，實際的攔截在事件總覽的 QC。
- 只呈現這個地震還差哪幾件事，不做分數、累計次數或排名。殘差類的任務不能靠刪除挑選直接消除，必須寫明原因。

**方向二：把這個階段需要的東西主動遞上來，像有一個助手。** 程式依目前的進度調整介面，不必由人手動切換。

佐證：

- 定出震央之後，波形自動改為依震央距排列，並提示已經改變。
- 挑完第一站之後，地圖自動放大到最近幾站的範圍。
- 點開某個任務時，地圖移到那個任務的範圍。

示範備註：任務列表預設關閉，示範前要先打開。其他可以示範的畫面有切地震的時間軸與波形牆、定地震的規模量測與方位角空隙。

## 四、接上現行流程

**方向：每一段都能單獨接上現行流程，分階段替換，不必一次全換（回扣第七週）。**

| 階段 | 匯出 | 交給現行流程的哪一段 |
|---|---|---|
| 切地震 | 事件波形檔 | 現行的挑波程式 |
| 定地震 | 相位檔 | 現行的 QC 程式 |
| 入庫前 | 入庫包 | 現行的入庫與發布 |

佐證：

- 新舊產出一致：相位檔讀入再寫出逐位元組相同（兩天共 263 個檔案）。依原始碼重寫切事件的做法，重新製作 228 個事件波形檔，全部逐位元組相同。這是第七週特性測試的延續，先證明行為一致，再談改善。
- 系統只標到「可入庫」並產出入庫包，實際的入庫仍由承辦把檔案歸位。
- 入庫包匯出時以舊的檢查程式再執行一次，找出規則庫的缺口。
- 原型已連同修改歷史併入同一個程式庫（10/31 改變 10/27 的決定，因為改寫結構的成本高而收穫少），已在測試機打包試跑，尚未發布給同仁使用。

## 五、新的處理想法

**方向：提出新的做法，讓處理更標準、步驟更少。** 這些想法都放在實驗性功能，由使用者試用後再決定去留。

- 自動權重：讓處理標準化。教材沒有「多清楚算清楚」的數值，各人的習慣因此有差異，改以訊噪比算出建議的權重。佐證：兩天的統計顯示同仁給的權重與訊噪比關係一致。目前改用起始分析的訊噪比，門檻與同仁確認之前不視為定案。
- 先挑再關聯：看到就先挑，再組成地震，可以減少許多步驟。原本要先開一個事件才能挑，但距離很遠時看到一個地震，不確定是不是同一個。挑了發現不是就要刪掉，其實已經挑好的挑選應該先留著，看是不是其他地震。佐證：把同一時間窗的挑選混在一起交給關聯程式，119 個事件找回 108 個。

## 六、開發的時間成本

**方向：Agent 降低了撰寫程式與功能的成本，但軟體開發有很大一部分在設計的迭代，仍然很花時間。** 這一段是給學員的心理建設：使用 Agent 開發時，要預留設計迭代與驗證的時間，功能做出來並不代表接近完成。

示意圖 `assets/week8-diagrams/w8-sdlc-cost.svg`：以軟體開發生命週期對照過去與使用 Agent 之後的時間成本。

- 過去：時間主要花在設計時規劃資料庫與資料格式，以及實作時撰寫功能與重構。
- 使用 Agent 之後：實作很快完成，時間轉移到設計與測試驗證之間的反覆迭代。

- 功能做得快就會做更多功能，要測試的項目與一次要考慮的事情也隨之增加，因此要把每個功能拆到可以獨立開關、獨立驗證。
- 自動測試能處理格式與計算。操作是否順手、畫面是否合理，只能由人實際使用來判斷，必須反覆提出修改才接近需要的樣子。

佐證：

- 10/21 至 11/01 的 app 修改約 268 筆，其中 202 筆只改畫面。筆數不等於時間，只作為參考。
- 標準差截斷：21 分鐘內修改 7 次，最後拿掉滑桿，改為三個按鈕。需求要看到畫面才能確定。
- 波形移到獨立視窗：功能完成後，實際操作才發現點選沒有反應、畫布大小不正確，10 分鐘內修改 6 次。
- 這個系統開發至今約兩週。能在短時間內做出原型，是因為有舊程式可以參考，開發者對這個主題也已有研究。目前還有很多流程上的細節需要細修與迭代，要做到完整並交給使用者測試，過程還會很長。

### 軟體與組織一起演化

軟體反映組織的流程與溝通方式，這個觀察稱為康威定律（Conway's Law，Melvin Conway 1968）。

- 現行系統：組織的結構已經與當初設計軟體時不同，因此陸續補上許多新的模組，這些修補反映出整個組織實際運作的樣子。
- 新系統：一開始的設計，實際使用時可能與原本的運作方式產生摩擦，要經由迭代才能符合實際情況，這就是花時間的地方。
- 周邊也可能跟著調整：組織的分工可能轉變，例如給一個人一個時間段，從頭處理到尾。基礎設施也可能改變，例如切地震要頻繁讀取網路硬碟上的連續波形檔，存放與讀取的方式就要重新調整。

## 下一步的方向

- 互動式教學：選出幾個案例，在系統上以引導的方式教導操作，可以沿用任務列表的形式，降低培養新人的門檻。日後也可以作為學校的教具，引發大家對地震領域的興趣。
- 自動挑波：以機器學習模型自動挑波並關聯成粗略的事件，作為切事件的參考，結果仍由人確認。內部已有部分在進行。
- 物理方法的檢查與機器學習保持獨立，例如起始分析與測站品質，日後可以用來攔截自動挑波的錯誤。

## 結語：人與 Agent 的分工

- 人負責的事：決定範圍與方向、請教使用者、實際操作驗證、決定門檻何時定案。
- Agent 負責的事：依人的方向實作系統、對照原始碼與實際資料查證、以統計整理同仁的判斷。

## 討論與交換意見

- 形式：講述時可以隨時討論，之後的時間留給學員提出題目、逐一討論。
- 可能的討論題：
  - 自己的業務中，哪一個沿用多年的檔案格式已經不敷使用，卻因為多支程式依賴而難以更改。
  - 有沒有相鄰領域的成熟做法可以參考。
  - 手上的工具有哪些功能的用途沒有寫下，只有使用者知道。
  - 交給 Agent 之後，哪些成果只有自己實際使用才能驗證。
