# 第五週草稿｜為什麼用 Domain Storytelling 分析工作

> 狀態：供討論的初稿，尚未放入正式教材。延續第四週的 Story 圖；取材自使用者 2026-09-23 提出的方向，以及 `kb/tools/domain-storytelling.md`。

## 從第四週的圖繼續往下走

第四週已經讓學員試著描述一件工作，並用 Domain Storytelling 畫出現況。第五週可以回頭說清楚：為什麼選這種方法分析工作？畫出的圖又如何協助後續實作？

當 Agent 開始擔任工程師，人與 Agent 之間需要先對要處理的工作達成共識。文字可以說明需求，但只寫「協助整理研究資料」這類句子，仍看不出資料從哪裡來、誰負責整理、結果交給誰，以及哪一步需要人判斷。Story 圖把這些關係放在同一個畫面上：演員執行活動，使用或產生工作物件，再交給下一位演員。參與者可以沿著編號活動逐句確認，發現彼此理解不同的位置。[Domain Storytelling 入門指南](https://domainstorytelling.org/quick-start-guide)

這也連到 DDD（領域驅動設計）的一個基本想法：開發程式的人需要理解業務使用的詞語與規則，並在討論、圖和程式中維持一致的說法。現在負責撰寫程式的可能是 Agent，因此領域專家更需要有辦法檢查 Agent 是否理解了工作。Story 圖提供了文字之外的共同討論材料。[Domain Storytelling 與 DDD](https://domainstorytelling.org/domain-driven-design)

## 為什麼現在更容易使用這種方法

以前要自行繪製 Story 圖，必須逐一拖拉圖形、安排版面，還要選擇合適的圖示。這些工作會佔用原本應該用來討論業務的時間。現在可以先口述一次具體案例，請 Agent 整理成「誰對什麼物件做了什麼」的活動句，再請它產生圖。人只需逐句確認：活動是否真的發生、物件名稱是否正確、交接是否遺漏。修正句子後，Agent 可以重新產圖。

圖產得更快，便可以把時間用在比較不同畫法與討論改進之處。例如第一版只有一位演員，可能看不出資料由誰提供；補入另一個人或系統後，交接位置就浮現出來。若某支箭頭接不上下一支，便要追問中間缺少的資料或判斷。

## 圖如何幫忙界定自動化的範圍

一整件工作通常太大，無法直接交給 Agent 實作。Story 圖讓我們沿著活動與工作物件，選出起點和終點清楚的一段。例如第四週的研究流程可以先選「研究者提出研究問題 → 檢索文獻 → 形成論文清單 → 研究者檢查」；暫時不把選定研究方法與撰寫報告一起納入。

選出這一段後，可以直接在圖上討論：哪支箭頭適合由 Agent 執行？它需要讀取什麼？應留下什麼結果供研究者檢查？研究者在哪裡核准或退回？第一版現況圖和加入 Agent 的第二版圖並列，就能看見改動的範圍。這使「想要自動化」成為可以逐步討論的具體工作。

## 圖怎麼走到規格與程式碼

從 Story 圖到程式碼，中間需要一次轉換。圖指出演員、活動與工作物件；規格則要補充每一段的輸入、輸出、完成條件與例外情況。以上述文獻檢索為例，圖上寫「Agent 整理論文清單」，規格還要說明清單應包含哪些欄位、如何保留來源、找不到資料時如何回報，以及由誰決定清單能否用於下一步。

Agent 可以依這份規格撰寫程式：接收研究問題、檢索指定來源、整理附來源的候選清單，最後交由研究者檢查。程式中的名稱也應沿用已確認的業務語言，讓人能從圖找到規格，再從規格找到對應的程式行為。圖本身不會自動變成完整程式；具體案例轉成需求後，才有足夠依據討論如何實作與驗收。[從故事形成需求](https://domainstorytelling.org/requirements)

第五週要強調的，是這條可反覆修正的路徑：**口述一次工作 → 畫出現況 → 選出一段 → 討論 Agent 如何介入 → 補足規格 → 實作並檢查。** Agent 可以協助畫圖與寫程式；人透過圖和規格確認它處理的是不是原本要改善的工作。
