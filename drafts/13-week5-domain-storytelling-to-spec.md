# 第五週草稿｜從 Domain Storytelling 到可實作的規格

> 狀態：供討論的初稿，尚未排入正式教材或投影片。延續第四週的研究流程案例；取材自 `lessons/03-back-to-your-work.qmd`、`kb/tools/domain-storytelling.md`、`drafts/10-week4-2-slides.md`，以及 2026-09-23 使用者提出的第五週方向。外部依據見文末。

## 為什麼要再談一次 Story 圖

第四週已經畫出工作的現況，也試著將 Agent 放入流程。第五週需要回答更根本的問題：為什麼要費力描述工作，而不直接請 Agent 寫一套工具？

現在 Agent 可以擔任程式工程師，將需求轉成可執行的程式。真正困難的地方隨之往前移：我們是否知道該自動化哪一段、輸入和輸出是什麼、哪些判斷不能交給程式？如果這些問題沒有釐清，Agent 仍可能寫出能運作、卻不符合業務的程式。

Domain Storytelling 讓領域專家敘述一次實際發生的工作：誰執行活動、使用什麼材料、產生什麼物件、交予誰處理。圖上的每支編號箭頭都能讀成一句話，參與者可以立即指出遺漏、誤解與用詞不一致之處。它是共同討論工作的工具，不是畫完便可直接交付的系統藍圖。[方法的圖形語言與工作坊說明](https://domainstorytelling.org/quick-start-guide)

過去建立這類圖，常需自行拖拉圖形、安排版面、挑選圖示。這些操作成本容易讓討論停在「有沒有畫圖」，而沒有進入「這個流程是否正確」。現在可以先口述案例，請 Agent 整理活動句、產生 PlantUML 圖檔，再由領域專家逐句修正。Agent 節省的是記錄與重畫的時間；對流程的判斷仍由熟悉業務的人負責。官方工具比較也指出，PlantUML 適合由文字保存並產生圖；現場共同建模則可以使用 Egon.io 等工具。[工具比較](https://domainstorytelling.org/articles/best-tool/)

## 圖為什麼能協助界定自動化範圍

「把研究流程自動化」涵蓋太多不同活動。若沿著現況圖讀取每支箭頭，就可以選出一段有明確起點、終點與交接人的工作。例如第四週的研究案例，可以先只討論「依研究問題檢索文獻，形成可供研究者檢查的論文清單」。

這一段的起點是**研究問題**，終點是**附來源的論文清單**。Agent 可以執行檢索與整理；研究者仍須判斷檢索範圍是否恰當，以及哪些文獻足以支持後續方法選擇。範圍縮小後，所需資料、外部系統、錯誤處理與人的核准位置才有辦法逐一說清楚。

圖上有三種值得停下來討論的位置：

1. **物件交接**：上一位演員交出的物件，下一位是否能直接使用？若不能，缺少什麼欄位、來源或說明？
2. **重複活動**：哪些步驟每次依相同規則執行？這裡可能適合一般程式；需要讀取不整齊材料或彈性整理時，才評估 Agent。
3. **判斷活動**：誰能決定方法、核准結果與承擔後果？這些責任應在第二版圖中明確保留。

因此，Story 圖不是用來證明每支箭頭都值得自動化。它讓我們看見一段候選工作與前後活動的關係，並在投入實作前討論哪些地方需要改進。

## DDD 提供哪些共同語言

Domain-Driven Design（DDD，領域驅動設計）強調讓軟體設計反映業務中的概念與規則，並由領域專家與開發者持續形成一致的語言。當 Agent 承擔程式實作，這項要求更具體：人、Agent、圖、規格與程式碼都應使用可追溯的業務名稱。[DDD 與 Domain Storytelling](https://domainstorytelling.org/domain-driven-design)、[DDD 概述](https://martinfowler.com/bliki/DomainDrivenDesign.html)

這裡先介紹三個夠用的概念：

- **領域與領域專家**：領域是要處理的業務問題，例如研究者如何整理文獻以決定方法。研究者知道何種來源可用、何種結論需要再次查證；Agent 不會因為能撰寫程式就自動取得這些知識。
- **共同語言**：圖上若寫「論文清單」，規格與程式就應說明它的意義，例如每筆資料需要題名、來源與取得時間。不要在另一處悄悄把它改稱「研究證據」；兩者可能不是同一個概念。共同語言需要在討論和實作中反覆修正。[共同語言說明](https://martinfowler.com/bliki/UbiquitousLanguage.html)
- **限界脈絡**：同一個詞在不同工作範圍可能有不同意義。「已核准」在研究流程可能表示方法已由研究者確認，在資料申請流程則可能表示資料使用權已通過審核。先說清楚這套語言適用的範圍，跨範圍時再明確轉換，避免把整個機關壓成一套含糊的資料模型。[限界脈絡說明](https://martinfowler.com/bliki/BoundedContext.html)

Domain Storytelling 是協助發現這些概念的建模方法，DDD 則提供將概念帶入軟體設計的思路。圖上的每位演員不必變成一個程式類別，每支箭頭也不必變成一個函式。先確認業務意義，再決定技術結構。

## 圖怎麼逐步變成程式碼

這裡有兩種不同的「程式碼」。第一種是 `.puml` 之類的**圖形原始檔**：Agent 依活動句撰寫它，繪圖工具輸出 Story 圖。第二種才是執行業務的**應用程式碼**。兩者之間還需要一份可檢查的規格。Domain Storytelling 官方也提醒，從具體情境直接跳到程式通常過於困難，應先將故事轉成可討論的需求。[從故事形成需求](https://domainstorytelling.org/requirements)

以「研究問題 → 附來源的論文清單 → 研究者檢查」這一段為例：

| 從圖讀到的內容 | 轉成規格時要補充 | 可能對應的程式結構 |
|---|---|---|
| 研究者提出研究問題 | 問題的必填內容、可接受的範圍 | 輸入資料結構與驗證規則 |
| Agent 向文獻來源檢索 | 可使用的來源、檢索條件、權限與筆數限制 | 檢索介面與外部服務連接器 |
| Agent 整理論文清單 | 每筆書目與來源欄位、去重規則、排序方式 | `PaperCandidate`、`PaperList` 等領域資料與整理邏輯 |
| 研究者檢查清單 | 核准或退回的標準、由誰操作、如何記錄理由 | 審核狀態與操作紀錄 |

上表只是對照，不是自動轉換公式。圖會指出「發生什麼事」，規格還必須補足「在什麼條件下算完成」。例如：檢索來源無法連線時如何回報？資料缺少出處時是否可列入清單？研究者退回之後，下一版如何保留修改紀錄？這些都需要由人與 Agent 共同追問。

可以將選出的工作寫成一份小型規格：

- **目的**：協助研究者從研究問題取得可查證的文獻候選清單。
- **範圍**：僅負責檢索、去重、整理與送審；不自動選定研究方法。
- **輸入**：研究問題、時間範圍、允許檢索的來源。
- **輸出**：每筆含題名、作者、年份、來源連結及納入理由的候選清單。
- **例外**：來源無法連線、文獻缺少必要欄位、候選數量超限時，回報原因並保留已取得的結果。
- **核准**：研究者可接受或退回清單，並記錄理由；核准不代表文獻結論已獲證實。
- **完成證據**：保存查詢條件、來源、產出時間、清單版本與研究者的決定。

當規格可供領域專家檢查，Agent 才適合據此撰寫程式。程式可以使用 `ResearchQuestion`、`PaperCandidate` 與 `ReviewDecision` 等名稱，讓輸入驗證、檢索、整理與人工核准各有位置。驗收時再用具體案例檢查：正常檢索是否產出可追溯清單？缺少來源的候選是否被標示？來源失效時是否確實回報？研究者退回後是否保留原版本？

這條路線可以表達為：**實際案例 → 現況 Story 圖 → 候選自動化範圍 → 未來 Story 圖 → 規格與驗收例子 → 程式與試用回饋**。每一次試用若發現業務說法不準確，應回到故事與規格修正，再更新程式；圖不會在程式完成後失去用途。

## 第五週可進行的練習

延續第四週的兩版圖，請學員各自選取一段工作。先說明選擇理由、起點與終點，再與 Agent 補成上述規格。交換給另一位學員閱讀：對方若只看圖與規格，能否說出系統要接收什麼、交付什麼、何時請人判斷，以及什麼情況應停止或退回？

練習的成果是一張經修正的 Story 圖、一份小型規格，以及三個能用來驗收的例子。是否撰寫程式，可依課程時間與學員需求決定；在動手實作之前，先確認這一段工作的邊界與業務用語。

## 尚待與使用者討論的取捨

- 第五週的主要示範要繼續使用研究案例，或改用署內學員帶來的一段實際業務？
- 課堂要讓 Agent 實作一個小程式，還是將重點放在從圖形成規格並互相驗收？
- DDD 是否先講共同語言與限界脈絡，將實體、值物件與聚合等程式設計概念留給後續實作？
