## 主線

承接原型之後，先以兩個案子的整體給出全貌（第二段），再依使用者 10/19 回想的經過講規則的整理（第三至第六段），最後是環境紀錄與 Agent 操作測試機（第七、八段）。

### 一、承接上週：原型

- 上一週以 vibe coding 做出預檢工具的原型，確認了畫面與操作。
- 原型實際上沒有丟棄：程式還改得動就先改，以回歸基準逐步改造，每一步都確認結果不變。
- 是否重寫留到上線對接之前：屆時依現有的技術框架與環境評估。
- 本週的重點是把原型背後的檢查規則整理清楚，讓工具有依據可循。

### 二、整體的全貌：兩個案子是一個整體

- 定位軟體翻新與預檢工具是同一個整體的兩個部分：挑波完成接著就是檢查，共用資料夾承載大量邏輯。
- 檢查程式自成一塊，挑波與檢查各自調用；規則不依賴兩端，兩端依賴規則。
- 兩邊的程式各自獨立運作，只靠波形檔與定位結果檔傳遞資訊。目前專案還小，檢查程式先與檢查端放在一起打包。

### 三、以投影片為主體，列出所有步驟

- 檢查的訓練投影片是整理的起點，照投影片原有的步驟編號與順序列出整個流程，不另訂新流程。
- 素材：開發端已有投影片步驟與程式處理的對照表，含投影片頁碼；送出前的檢查對應到投影片的前兩大步驟，入庫與回報不變。

### 四、逐步寫出對定位結果檔的操作與篩選

- 每個步驟寫清楚：讀取了什麼、依什麼條件篩選、門檻是多少、結果怎麼處理。
- 素材：規則檔記錄門檻、擋下或提示、處理方式。

### 五、整理成一張大表：規則怎麼建、怎麼分類、為什麼去留

本段要認真討論規則的建立、分類與去留，這些設計意圖都可以從大表的欄位看出來。以下依第 12 版的大表整理（2026-10-13）。

#### 規則怎麼建出來

- **先列來源做了什麼，再寫規則。** 每個來源逐項列出它實際做的事，記錄原文位置、條件、門檻與輸出；一個判斷條件一項，以原始碼的實際邏輯為準，不推測。
- **列出的不只是檢查。** 項目分成檢查、修正（改寫檔案）、篩選（決定是否入庫）、重跑、分流、步驟六種；照投影片只會看到檢查，舊程式裡的修正與篩選也會影響結果。
- **雙向對應。** 每一項來源條目要被規則接住、註明不納入的理由，或列為待決定；每一條規則要有來源，或註明沒有現行依據。

#### 怎麼分類

- **依定位結果檔上被檢查的對象分成 9 個項目：** 檔案格式、發震時間、震央位置、震源深度、規模、挑波、測站與資料量、定位品質、事件與入庫。分類不依來源，也不依舊程式，因為同一件事常分散在好幾個來源裡。
- **偵測與處理分開。** 大表的主體是檢查；「該不該重跑」與「入庫怎麼分流」另列成兩組規則，只寫觸發的條件與去向。入庫的篩選屬於入庫管理，不在預檢擋下。
- **規則以檢查的欄位與判斷命名，不寫門檻。** 門檻改變時，規則名稱不必跟著改。

#### 大表的欄位與設計意圖

| 欄位 | 內容 | 設計意圖 |
|---|---|---|
| 項目、規則、名稱 | 9 個項目，規則編號，以欄位與判斷命名 | 依檢查的對象分類；門檻不進名稱 |
| 目的 | 為什麼要檢查；待決定的列為要確認的問題 | 每條規則都要說得出理由，說不出理由的就是要討論的 |
| 檢查的欄位 | 讀取定位結果檔的哪些欄位 | 讓承辦知道去哪裡修，也讓網頁能標出原文的位置 |
| 建議處置 | 自動修正、重跑或人工處理的具體做法 | 檢查結果要能轉成動作；沒有具體做法的留空，不硬填 |
| 狀態 | 待確認、候選、不啟用、待決定（確認作法、新增規則、門檻不一致） | 記錄每一條規則的去留走到哪一步 |
| 程式 | 檢查中、未執行 | 區分寫在規則庫裡與程式實際在跑的 |
| 各來源欄 | 依年代由舊到新，分為現行與參考，★ 為主要依據 | 同一條規則在不同年代的門檻是否一致，橫向一眼看出 |
| 格子 | 來源條目的編號與門檻，可點開原文 | 每一格都能回到原文查證 |

來源另有一張表，列出每個來源被接住、不納入與待決定的條目數。有兩支排序與合併的舊程式，條目全部不納入，大表不列它們的欄位。

#### 為什麼有這些去留

- **不納入的理由。** 作業步驟、入庫後的作業、工具的其他功能選項、介面操作、改寫原檔的功能，不屬於送出前的檢查。
- **待決定分三類。** 確認作法（22 列）、新增規則（7 列）、門檻不一致（4 列）。不同來源的數值不一致時不由開發端裁定，整理成開會議題。
- **刪除的候選規則。** 第 12 版刪除沒有來源的候選規則，以及評估後沒有必要收錄的規則。
- **目前的數量。** 大表共 74 列：41 條規則（34 條待確認且程式執行、3 條待確認但不啟用、4 條候選且不啟用）與 33 列待決定，另有重跑與入庫分流兩組。規則全部是待確認，要由檢查端的同仁逐條確認。
- **檢查節點以程式執行。** 大表整理好之後，檢查的節點以一般程式依規則執行，不做成 Agent，也不採用 RAG：輸入與輸出都是可以預期的結構化資料，結果穩定、成本低。

### 六、規則要有依據

- 整理規則時，開發端使用大量的 Agent 盤查來源；盤查的結果需要反覆查閱與驗證，因此每條規則都要能回到原文。
- 每一條規則都要註明出自哪裡，大表上的每一格都能點進去查看原文。
- 依據不只投影片：舊程式的原始碼、其他文件與紙本清單也是來源，投影片沒寫到的檢查，可能藏在這些來源裡。
- 素材：查看來源的介面，可開到投影片的頁碼、文件的頁面或原始碼的行號。

### 七、把環境記錄下來

- 正式工具的環境要能重現：記錄 Python 的版本與套件，複雜時包成映像檔。
- 素材：第七週候選素材「把環境記錄下來，讓它可以重現」。

### 八、由 Agent 操作測試機

- 舊程式只能在 Windows 上執行；所有工作從 Mac 進行，由 Agent 透過 SSH 在 Windows 測試機上執行。
- 素材：第七週候選素材「由 Agent 操作測試機」與分工圖。

- 「vibe 通常是不會管環境的，因為 agent 都幫他搞定了，但這個東西需要有記錄，甚至如果複雜一點會包成 image 之類的」（10/06）
- 「很多東西其實我們在 prototype 的時候，因為這個東西做出來就是某種程度上是要被丟棄的，那其實有些太細的工可以不用馬上做」（10/06）
- 「如果這 prototype 最後會變成一個自己用的小工具，那就會有些東西也是要顧及的，那我們線畫在這好了，就是哪些東西做成小工具是不用的」（10/06）
- 「這邊可以把現在的硬體設定帶一下……算是展示一下說 agent 可以自己 ssh 去控制其他電腦」（10/05）
- 「我之後應該做成我都從 mac 做，然後叫 agent 自己 ssh 去 win 上面……跑 test……就不會有這種格式轉來轉去還有討論歷史不連貫的問題？」（10/05）
- 「這個遠端測試設定就比較像是我自己比較習慣用 mac 才會這樣做，那如果原本就在 win 上面不用這麼麻煩，但是換個角度就是 win 上面開發 linux 程式也可以透過這個方式直接控制 server，或是控制 wsl」（10/06）
- 「可能 agent 變成主要的重點，因為是凸顯 agent 可以做的事情，還有人可以拉出 mac」（10/08）
- 「簡報本身還是在課堂裡面，所以對象是所有人，然後就是不是只報進度，就是整個設計邏輯也要講，還有哪邊 ai 有幫忙」（10/17）
- 「像是我們實際上在做的事情就是有點像是在建規則資料庫，然後程式依照規則去 qc，那我們會選用一般程式規則而不是 agent rag 也是這樣比較穩定且成本低，而且輸入輸出都是可以預期的結構化資料，所以才沒有把節點搞成一個 agent，但是開發在梳理規則的時候用了超級大量的 agent 去盤查，而且還需要反覆查閱跟驗證，所以才做了一個可以點進去看來源的一個介面」（10/17）
- 「我應該會把現在兩個案子當作是一個整體的兩個部分，就是裡面有個［共用資料夾］，是很多邏輯都在裡面，而且 pick 完就是接 qc，流程是緊密的，但是兩邊的程式碼要能夠獨立運作，只靠 afile pfile 等檔案傳遞訊息」（10/17）
- 「應該說檢查程式本身是自己一塊，然後挑波跟 qc 各自去調用」（10/17）
- 「目前是先放在一起，但是邏輯上他是獨立的，就是規則不依賴 qc 跟 pick，是 qc 跟 pick 依賴這個規則，只是目前專案還不大先這樣打包而已」（10/17）
- 「可能一開始說要做簡報說的太快了，應該目前是要先把文稿寫出來」（10/17）
- 「這週的範圍主題比較像是把 qc 規則整理這段講清楚，所以就是先講上次做了一個 prototype ，這週就是認真的把整個流程給整理出來，一開始根據 qc 的投影片作為主體，照著上面的流程把整個步驟都列出來，然後每個步驟到底對 pfile 做了哪些操作與篩選，然後整理出一個大表格來統整這些規則，我們也要規則是有依據的，就會可以點進去看規則」（10/19）
- 「兩個案子的整體、環境紀錄和測試機 這個可以放，我剛剛比較像是在回想」（10/19）
- 「不另成一段，在規則依據那段說明來源不只投影片就好」（10/19）
- 「照你建議的位置放」（10/19，回覆上述兩點的位置）
- 「原型可以丟棄 這個其實目前實際上也沒有丟棄」（10/19）
- 「保留原型的設計，逐步遷移 比較像是還改得動就先改，我們整個要上線對接之前，要看原本現有技術框架與環境，那時候才會評估是不是要重寫」（10/19）
- 「規則的部分應該是有考察出來，然後重新看了一下新增的條目到底是什麼，去評估又沒有必要收錄」（10/19）
- 「我們應該是會要比較認真的去討論這些規則是怎麼建出來，怎麼分類，還有為什麼有這些去留，這個應該在大表上的欄位可以看出這個設計意圖」（10/19）
