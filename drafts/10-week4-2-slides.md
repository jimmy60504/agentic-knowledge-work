### 3｜Story 圖的三個元素

**畫面**

- 主訊息：一張 story 圖只有三個元素：演員、工作物件、編號活動。
- 演員：人、單位或系統；文獻資料庫、計算環境亦屬演員
- 工作物件：文件、資料、對話等在演員之間傳遞的物件
- 活動：帶編號的箭頭，寫成動詞；自 1 號讀至最後，整張圖可讀成一段敘述
- 一張圖描述一個具體案例，不畫分支；粗顆粒描述整件，細顆粒描述一段

**筆記**

圖的任務：以研究流程圖的前兩句為例，以註記標出演員（人、系統）、工作物件、編號活動；圖檔 `slides/story/w42-elements.svg`
版型：流程

上半場的研究流程圖依此畫成：演員有研究者、資料管理者、審閱者三個人，文獻資料庫、計算環境兩個系統；工作物件是研究問題、論文清單、方法與評估指標、整理後資料、程式碼、結果圖表、比較表、結論、報告、審閱意見；活動十一個，各有編號。這種畫法叫 domain storytelling，元素只有三種，畫的時候每次一句：何人、何動作、交出何物。自 1 號讀至最後，整張圖可讀成一段敘述；不通順之處即是圖畫錯或事情尚未想清楚之處。

兩個要點。第一，系統也是演員：資料庫、計算環境、既有的業務系統皆畫為演員，因為工作物件會交予它們、再由它們交出；只畫人，圖上便無法看出系統在何處接手。第二，一張圖只講一個具體案例，不畫所有分支；有分支就多畫一張。粗顆粒講整件事，細顆粒講其中一段。上半場六種介入方式各一張圖，就是同一件事的六段細圖。

**原話與來源**

- 來源：[[domain-storytelling]]

### 4｜一行一句的文法

**畫面**

- 主訊息：畫圖之前先寫句子，一行一句：演員、動詞、工作物件。
| 句型 | 例句 |
|---|---|
| 演員 ＋ 動詞 ＋ 物件 | 研究者 寫下 研究問題 |
| 演員 ＋ 動詞 ＋ 物件 ＋ 動詞 ＋ 下一個物件 | 研究者 依 比較表 歸納出 結論 |
| 演員 ＋ 動詞 ＋ 物件 ＋ 介詞 ＋ 演員 | 研究者 撰寫 報告 送交 審閱者 |

- 動詞寫在箭頭上，受詞是箭頭指到的物件；不寫「得到」這類結果詞
- 物件須相互銜接：上一句交出的物件，是下一句的依據
- 演員交替之處即交接點，也是完成證據與驗收的位置

**筆記**

圖的任務：表格三列各對應一句，旁附三句畫成的圖；圖檔 `slides/story/w42-grammar.svg`
版型：總覽

圖是句子的畫法，先寫句子，再產圖。句子只有三種：演員以動詞產出物件；演員依上一個物件產出下一個物件；演員產出物件交予另一個演員。第一種是起點，第二種把物件串接，第三種是交替。上半場的圖自 1 號讀至 11 號，每一句皆為這三種之一。

三個規則。第一，動詞寫在箭頭上，受詞是箭頭指到的物件；「檢索文獻，得到論文清單」不成一句，「研究者 向 文獻資料庫 檢索出 論文清單」才是。第二，物件須相互銜接：論文清單是選定方法的依據，方法是撰寫程式的依據，句子裡寫出來，圖上才有連線；沒有連線的物件即是沒有後續的產物，本身即是一項發現。第三，演員交替之處即交接點：研究者把報告送交審閱者，審閱者以審閱意見交回；每一個交接點都是一份工作物件交出的位置，也是下午要寫完成證據與驗收的位置。

句子是 Agent 能寫、人能改的形式，這是下一頁的前提。

**原話與來源**

- 「我感覺沒有完整的文法結構？就是變成得到一堆東西而已？沒有受詞？」（09-22）
- 「原本論文清單裡面去選出主要方法，這個有要連起來嗎？因為感覺看圖覺得沒有關聯？」（09-22）
- 來源：[[domain-storytelling]]「寫故事給 agent 的規則」

### 5｜請 Agent 畫圖

**畫面**

- 主訊息：人口述一次實際完成的工作，Agent 寫成句子與文字檔，工具產圖；修改只改句子。
- 口述：實際完成的一次，自始至終，包括交付對象與交付物
- Agent 列出演員、工作物件與活動句，人逐句確認
- Agent 把句子寫成 PlantUML 文字檔，工具產出圖；本機安裝或線上服務皆可

```text
Person(researcher, 研究者)
System(litdb, 文獻資料庫)
Document(papers, 論文清單)
activity(_, researcher, 依研究問題向, litdb, 檢索出, papers)
```

- 修改不重畫：修改句子，重新產圖；文字檔存入自己的 repo

**筆記**

圖的任務：這一頁的流程本身畫成一張 story 圖：講師口述，Agent 列句、寫文字檔，工具產圖，講師通讀後回到句子修改；圖檔 `slides/story/w42-agent-draws.svg`
版型：流程

上半場所有的圖皆依此產生。講師把研究流程口述給 Agent：實際完成的一次，自提出問題至收到審閱意見；Agent 先列出演員、工作物件與活動句，講師逐句修改；確認之後 Agent 把句子寫成 PlantUML 的文字檔，用的是 DomainStory 函式庫，一行一個元素、一行一句活動，工具讀這個檔產出圖。畫面上的四行即是文字檔的形式：宣告演員與物件，再寫活動句，編號自動遞增。整張研究流程圖的文字檔只有二十多行，附在講義。

各位可依此進行。任何一個 agent 皆能撰寫這種文字檔，口述時不必使用它的語法，以日常語句說一次，缺漏之處 Agent 會追問。產圖有三條路：本機安裝 PlantUML；把文字檔貼到 PlantUML 的線上服務；或用 domain storytelling 官方的 Egon.io 手動畫。前兩條可以由 Agent 直接產圖，第三條圖由人畫，Agent 只出句子。

要點是修改不重畫。圖有錯，回到句子修改，重新產圖；文字檔存入自己的 repo，下次修改業務流程時自這個檔改起。這與這門課的做法相同：內容改文字，版面交給工具。

現場操作（第一輪，約四分鐘）：這一頁講完即切到 Agent 視窗，在課程 repo 內進行。口述說法：「我要把一件工作畫成 domain story。照 kb/tools/domain-storytelling.md 的句型，先把我說的整理成一行一句，先不要產圖。這件事是這樣：我有一個研究想法，先到文獻資料庫找論文，讀過之後選定方法和評估指標，向資料管理者申請資料並整理好，照方法寫程式，在計算環境用資料跑出結果圖表，和現行方法比較做成比較表，再歸納結論寫成報告，交給審閱者，收到審閱意見。」Agent 列出句子後，投影出來逐句讀，當場改一兩句用詞，再說：「句子確定，寫成 PlantUML 的 DomainStory 文字檔，存到 slides/story/live-research.puml，用 slides/story/render.py 產圖。」圖出來即投影。口述時刻意用平常說話的方式，不用語法，讓學員看到 Agent 會自行補成句型；缺的部分它會追問，追問即回答。

- 圖下：
1. 研究者 寫下 研究問題

版型：案例

第一版的條件只有一個：照實。畫實際完成的一次，不畫理想的做法，也不畫 Agent。三種常見的偏差。第一，先把 Agent 畫入：如此無法看出現況，也無法看出介入前後的差異；Agent 留至第二版。第二，把執行不順的步驟省略或美化：例如申請資料等候兩週、比較表以人工整理，這些照實畫，因為那正是下一段要找的缺口。第三，把由人決定的活動省略：選定方法、歸納結論由人執行，仍須畫上，圖上才能看出哪些活動不交付。

這張圖即是工作單的上區。下午第一件事是與 Agent 畫這張圖，各位提供事實，Agent 提供句子與圖，至通順為止。

### 13｜拆解的原則

**畫面**

- 主訊息：別人的 Agent 讀成一句：執行何種動作、留下何種產物、交予誰驗收。
- 四個實例拆解之後結構相同：Agent 演員、箭頭上的動詞、指到的物件、交予的人
- 動作十個、產物四類、驗收點分事前與事後
- 三題皆能回答的活動可寫入工作單；無法回答的那一題，即是尚不能交付的原因

**筆記**

圖的任務：一句 story 句型拆成三格：Agent →動詞→ 物件 →交予→ 人，三格之下各標一個問題與答案的範圍：十個動作、四類產物、事前與事後
版型：對比

四個實例看似四件不同的事，讀成句子之後結構相同：Agent 這個演員，箭頭上一個動詞，指到一個物件，交予一個人。所以任何用法都可以依三個問題拆解。第一個問題，Agent 執行何種動作：查找、讀取、擷取、比對、計算、草擬，動作的種類有限。第二個問題，留下何種產物：一份答覆、一份底稿、一張事件卡、一張欄位表，產物決定人取得後能否檢查。第三個問題，人在何處驗收：事前設定標準、門檻、範圍，事後檢查、接受或退回。三個問題答完，一個用法即拆解完成。

| 結果圖表直接製成比較表，參數與例外未交代 | 逐次實驗紀錄表，附參數、資料範圍與排除註記 | 參數是否一致、例外如何處理、比較表能否重現 |

- 尋找 C 的來源：詢問 AI、請 AI 搜尋、自行閱讀、請教同事、實地觀察、親手試作

**筆記**

圖的任務：結果圖表（A）、逐次實驗紀錄表（C）、比較表（B）一列橫排，Agent 填寫紀錄表、研究者檢查、Agent 依核准的紀錄表製表；讓人看出 C 是插在 A 與 B 之間、可以檢查的一站；圖檔 `slides/story/w42-a-c-b.svg`
版型：流程

B 定義為完成證據之後，常會發現 A 無法直接到達 B。先說明原因。人的想法轉為文字或畫面時經過選擇，對方看到的是表達，不是意圖；人與人如此，人與 Agent 亦然。因此協作需要一個可以共同檢視的中間產物：一段整理、一份有依據的文稿、一張比較表、一個具體的問題描述。LLM 學過大量人類語言與互動模式，可以借用溝通、管理與教練的方法，把意圖、背景、分工與標準說清楚，提高它產生合適回應的機率。互動形式像同事或教練，不代表它具有人的動機或責任。

再說明如何尋找。A 到 B 無法說清或做不可靠，即找一個中間節點 C，把工作拆為 A 到 C、C 到 B。C 可以是資料、決定、規格、草稿或試作結果，條件是補上一個具體缺口、讓下一步有依據、讓人能檢查。需要幾層視任務、人的理解與工具能力而定；同一層可以反覆修改。尋找 C 的來源不止一種：詢問 AI、請 AI 搜尋、自行閱讀、請教同事、實地觀察、親手試作。Agent 的建議先視為候選，再以材料或試作確認。成品出現內容問題，回到適當的草稿層修改，不在版面上重做。

三個例子。前兩個是第二週的做法：想法直接轉為簡報，C 是一份結構化的文稿；文稿轉為簡報，C 是逐頁稿。第二週的三個迴圈即是三個 C，簡短提及即可。第三個是本週的案例，也是第 15 頁標為無法銜接的那一步：結果圖表直接製成比較表，參數與例外尚未交代，C 是逐次實驗紀錄表附參數、資料範圍與排除註記，人檢查參數是否一致、例外如何處理、比較表能否重現。在圖上，C 是插在結果圖表與比較表之間的一個新工作物件；缺少它，結論即無法追溯。此即工作單「中間產物與完成證據」一欄的前半。

時間允許時可放三分鐘示範：先說幾個零散想法，請 Agent 寫成一段，當場指出一處偏移，補上理由，請它重寫。時間不足則略過。

**筆記**

圖的任務：無，引文即畫面

有了 C，才有分工的問題。第一，角色會輪替。上半場「Agent 的角色」一頁列了三群角色；一段工作從 A 到 C 到 B，同一個 Agent 常先擔任討論者，再擔任起草者，最後擔任審查者檢視自己的產出。請教時帶著自己的意見提問；交辦時說明目的、所需結果、限制與檢查標準，做法由它選擇。

第二，人核准哪一步須先行約定。判定與高影響的處置由有權責的人決定，Agent 列出依據、選項與疑點。第 15 頁標為核准點的活動即是這些，下午填表時即為「誰驗收」一欄。

第三，畫面上的引文是製作工具在一段工作中的分工線：需要理解材料、提出選項、試作的部分交給 Agent 探索；規則一旦確定，收斂為程式或既有工具反覆執行。以案例而言，方法與評估指標確定之後，前處理與執行實驗寫成腳本反覆執行，選定何種方法、如何歸納結論仍由人判斷。這門課本身也採同一做法：逐頁稿與 Agent 討論定稿，由一支程式產成簡報；story 圖與 Agent 討論句子，由工具產圖。
