# Agent 的產出方式：成果、狀態改變與持續服務

> 狀態（2026-09-19）：九類產出與三條界線已併入 [[agent-use-patterns]] 的「中間產物與完成證據」欄與一句提醒；本檔保留作演變紀錄，不進投影片。

整理日期：2026-09-19。本表是供盤點工作流程的**候選分類工具**，不是產品功能清單，也不是已定案的課程概念。使用者原先提出「圖文產品、可用程式碼、指令控制程式」三種例子；下表把它們放進可比較的層次。

## 重點

### 先問「最後留下什麼」，再問「Agent 做了哪個動作」

| 產出／效果 | 具體形式 | 地震工作中可想像的對照例子 | 驗收焦點 |
|---|---|---|---|
| **1. 給人閱讀或觀看的成品** | 報告、圖表、簡報、網頁、圖片、影音、解說稿 | 把已確認的地震資料整理成說明圖文或宣導材料 | 事實、來源、圖意、受眾、版權、對外說法 |
| **2. 給系統使用的結構化資料** | JSON、CSV、資料表、欄位抽取、分類標籤、索引 | 從歷次事件文件抽取日期、版本、修訂原因，建立待核對清單 | 欄位定義、漏件與誤判、來源可追溯、能否回復 |
| **3. 可執行的程式與設定** | 程式碼、測試、SQL 查詢、腳本、設定檔、規則 | 寫一段整理公開地震目錄、重算統計或檢查資料格式的程式 | 正確性、測試、環境與權限、執行後影響 |
| **4. 支持人判斷的分析** | 異常清單、證據比較、原因假說、選項與建議 | 比較不同版本的事件資訊，指出數值差異與尚缺證據 | 原始依據、不確定性、反例、誰有權下結論 |
| **5. 已完成的系統操作** | 呼叫 API、操作介面、建立工單、更新資料庫或檔案、執行程式 | 在授權環境中彙整測站異常並建立待查工單 | 操作前條件、權限、實際結果、紀錄、回復方式 |
| **6. 已送達的通知與交接** | Email、訊息、待辦、升級通報、交班摘要 | 把待查測站異常送給負責人，附時間、證據與未完成事項 | 收件人、時效、內容版本、送達與接手紀錄 |
| **7. 持續更新的監看結果** | 定期比對、異常提醒、狀態面板、週期報表 | 定期檢查公開資料頁或測站維運紀錄是否有變更 | 觸發門檻、誤報漏報、重複提醒、停止條件 |
| **8. 留給下一次的工作資產** | 知識庫條目、FAQ、SOP、檢查表、可重用工作流程 | 把核實過的常見問答、資料口徑與例外處理經驗回存 | 適用範圍、版本、維護責任、過時清理 |
| **9. 即時互動的答覆** | 依對話脈絡回答、追問缺少資訊、引導使用者完成查詢 | 依已發布的地震資訊回答「我所在地震度為何」，不自行發布新判定 | 資訊時效、引用來源、無法回答時如何轉介 |

1–4 和 8 主要留下**可審查的內容或檔案**；5–6 改變了外部系統或人的工作狀態；7 是**持續運行的服務**；9 在對話中逐次回應。持續服務每次觸發又可能產生其他類成果。這些類別可在同一任務中串起來，並非互斥。例如 Agent 先產生差異清單（2、4），經人確認後建立工單（5），再通知承辦人（6）。

### 三個容易混淆的界線

- **「寫出指令」不等於「執行成功」。** 產生 SQL、API 參數或操作計畫屬 3 或 4；真正呼叫工具並確認系統狀態改變才是 5。
- **「給建議」不等於「做決定」。** Agent 可列出依據、選項與疑點；發布判定、科學結論或高影響處置仍需有權責的人或既定系統決定。
- **「發出通知」不等於「對方收到並接手」。** 需要把送出、送達、確認與後續狀態分開記錄。

### 再拆一層：成品前面的中間產物

使用者舉「產出投影片」的例子：中間可能先有大綱、逐頁稿與 Python 腳本，由 Python 函式庫寫出 PPTX；最後還要開啟或渲染檢查。這是**一條具體實作路徑**，不是所有 Agent 都必須用 Python。其他成果也有自己的中間產物：寄信先形成收件人、主旨、內文與附件參數；填表先形成欄位資料與瀏覽器動作；定期監看先有排程、查詢條件與差異判定。詳見 [[openclaw-how-people-use-it]] 的「為什麼它能做」。

盤點時可加兩欄：**Agent 先寫下什麼？哪個工具或人真正讓事情發生？** 這能分辨模型產生的內容、工具執行的動作和人作出的核准。

若要從具體操作一路連到地震業務的工作動詞，見 [[agent-operation-output-business-map]] 的四層對照與完整案例。

另一個獨立問題是「Agent 接手業務到什麼程度」：從人向 Agent 請教、一次性交付、製作工具後退出，到固定節點呼叫模型、節點 Agent、跨節點協調。這些接手方式與本表的九種產出可以交叉搭配；對照見 [[agent-operation-output-business-map]]。

### 選題時加一個欄位

在「輸入 → 工作 → 產出 → 驗收」之外，補問：**Agent 的結果只供人閱讀，還是會寫入系統、通知他人或持續自動觸發？** 後三者需要額外確認權限、錯誤處理、紀錄與回復。這是工作設計上的推論，不表示每項成果都需要 Agent；格式固定、規則穩定的步驟可先考慮一般程式或現有系統。

## 洞見

- 使用者的三個例子已跨了兩個維度：**成品形式**（圖文、程式碼）和**作用方式**（指令使系統執行）。若只列「可以生成什麼格式」，會漏掉 Agent 真正改變工作流程的地方，也會把「寫好草稿」誤當成「完成發布」。
- 產出價值可看三層：當次得到可用成果、流程狀態真的前進、經驗能留給下一次。三者可以逐步增加，但每上一層都要重新確認驗收與責任，不能用產出數量代替成效。
- 對地震業務尤其要分清時效與影響：用公開資料做分析底稿、整理問答，與參與秒級警報或正式發布，是不同等級的工作。後者不能因技術上能呼叫 API 就視為適合交給 Agent。
