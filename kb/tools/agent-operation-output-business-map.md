整理日期：2026-09-19。這是供討論與盤點的**候選分析工具**，不是 Agent 功能的市場統計，也尚未定為課程正本。這裡的「完整」指涵蓋常見數位知識工作中**可觀察、可驗收的操作類型**；不同產品的工具、權限和環境不一，不能宣稱每個 Agent 都能執行每一項。

### 先講底層：Agent 如何讓事情發生

**模型主要產生文字形式的內容與動作描述。** 動作描述可能是一段指令、程式碼，也可能是符合工具規格的結構化呼叫（例如工具名稱加 JSON 參數）。它本身沒有手去按滑鼠，也不會只因為寫出「寄信」兩字就真的寄出。Agent 所在的 **harness（執行框架）** 預先接好可用工具與執行規則：收到模型的工具呼叫後，檢查可用性與權限，交給對應的程式執行，再把結果送回模型。模型可依結果提出下一步。[OpenClaw 的 Agent loop](https://docs.openclaw.ai/agent-loop)把這段過程列為訊息進入、組裝上下文、模型推論、工具執行與回覆。

```text
人的目標／事件
    ↓
模型讀取文字脈絡，產生回答或工具呼叫（名稱＋參數／指令）
    ↓
harness 呼叫預先接好的工具：終端機、程式、API、瀏覽器、滑鼠等
    ↓
工具真的讀取、計算、點擊、寫入或傳送，回報結果／錯誤
    ↓
模型依回饋繼續操作、請人確認，或交付成果
```

連「開一個 Markdown 檔，把討論寫進去」也需要這個循環：

1. 模型根據要求與工作區脈絡，決定檔案放哪裡、叫什麼、要寫哪些內容；必要時先呼叫工具查目錄與既有檔案。
2. 模型產生 Markdown 文字，並提出「建立／修改這個路徑的檔案」的工具呼叫；這一步仍只是文字與參數。
3. harness 將呼叫交給檔案工具、patch 工具或終端機；底層程式透過作業系統建立目錄／檔案並寫入位元組。
4. 工具回傳執行結果；模型再讀檔或查看差異，確認檔案真的存在、內容與位置正確，需要時修正。

因此，**單獨的 LLM 可以寫出 Markdown 內容，無法僅靠生成文字就在本機建立檔案**。寫檔與回讀是 harness 提供工具後，模型與工具往返完成的工作。若只要在對話框顯示 Markdown，最後一步是介面顯示文字，並未產生工作區檔案。

同理，「做投影片」可能由模型先寫逐頁稿與 Python 程式，harness 透過終端機執行 Python，由程式庫產生 PPTX，再開檔或渲染檢查。「操作網站」則可能是模型提出要點的元素或座標，瀏覽器／電腦操作工具執行點擊並回傳畫面。**模型提出動作、工具執行動作、結果得到驗證，是三件不同的事。** 有些工具直接提供「建立簡報」「建立工單」等較高層功能，模型不一定需要先寫程式；能做到哪一步取決於當時接好的工具和授權。

### Agent 的介入方式：接手範圍與介入程度

使用者 2026-09-21 補充現況判斷：目前最有收益的是第三種「建置工具後退出」，因為程式可預期、可測試、可重複、速度快，不受 Agent 不確定性影響，vibe coding 已開始改變大眾做法；第四到六種把模型放進運行中的流程，仍在探索階段，尚未形成共識。

使用者 2026-09-20 補充：六種也對應**信任程度**，Agent 越可信，用法會從第 1 種逐步走向第 6 種；但同時牽涉成本與採用的技術難度，不是單純的能力階梯。

這裡問的是**人把多少工作交給 Agent 接手、Agent 能自行做哪些步驟、何時交回人或一般程式**。使用者先提出請教、製作程式後退出、接入節點三種；下表把容易混在一起的相鄰用法攤開比較。它不是按數字遞增的單一能力等級：**建置時接手很多工作**，也可能讓 Agent 在**運行時完全退出**。因此要同時看接手範圍、參與時點與操作權。

| 接手方式 | Agent／模型接手到哪裡 | 同一個「測站異常」例子 | 要分清楚的界線 |
|---|---|---|---|
| **1. 對話**（原稱：人向 Agent 請教） | 人在正式系統流程之外發問；Agent 回答後退出，人自行查證與操作 | 同仁問斷訊的可能原因，拿待查清單自行排查 | Agent 對人的工作有影響，但沒有接入正式系統流程 |
| **2. 交辦**（原稱：Agent 完成一次性交付） | 人交辦一件工作；Agent 用工具查找、寫檔、驗證，交出檔案後退出 | 產出一份測站異常彙整報告或分析用的 CSV | 比單純建議多了可檢查的成品，但後續是否使用仍由人決定 |
| **3. 製作工具**（原稱：Agent 建置工具後退出） | 建置時產生程式、規則或設定；人測試、部署，後續由一般程式執行 | 寫好資料缺漏比對腳本，之後由排程固定執行 | 程式執行時若不再呼叫模型，就沒有運行中的 Agent |
| **4. 結構化判斷**（原稱：固定節點呼叫一次模型） | 既有程式把輸入送給模型，取回分類、摘要或欄位後照固定路徑走 | 系統把一則故障描述送去抽取測站編號，再交原流程處理 | 有模型參與，但模型不能選工具與下一步時，不必稱為 Agent |
| **5. 流程指派 Agent**（原稱：流程節點呼叫 Agent） | 事件到達時呼叫 Agent；它可查資料、選工具、迭代，交出結果給下一節點或人 | 新異常觸發 Agent 查日誌與維修史，做待查卡交值班者 | 運行時確有 Agent；仍須界定節點的輸入、時限、輸出與錯誤交接 |
| **6. Agent 管理流程**（原稱：Agent 協調跨節點工作） | Agent 按回饋選擇下一步，跨系統查找、建待辦、等待核准並追蹤 | 同一事件從查證、建待查單、通知到追進度，由 Agent 串接 | 要逐項指定哪些步驟可自動做、哪些要人核定；工具成功不等於整件業務完成 |

2026-09-21 補：六種名稱改短為「誰對誰做什麼」的句型，主詞從人到流程到 Agent，對應干預漸深；表內括注原稱，其他筆記引用舊名時以此對照。第 1 種改稱「對話」。使用者的分類軸是 Agent 干預流程的多寡，因此反向審查（人做、Agent 檢查）、模擬對象（扮民眾提問）、記錄者這類做法不是新的介入方式，而是對話裡的角色，與討論者、整理者同歸第 1 種；起草者與操作員會產出檔案，屬第 2 種。影子模式（Agent 並排判斷、不寫入、事後比對）與回測（用去年資料試新規則）同日提出，前者是第 4、5 種放權前的驗證做法，後者是第 3 種腳本的另一用途，暫未排進投影片。

第 4 種特意列出**模型使用但未必是 Agent**的比較組。[Anthropic 的說明](https://www.anthropic.com/engineering/building-effective-agents)區分由程式預定路徑的工作流，以及由模型動態決定過程與工具的 Agent；實作未必有絕對分界，應看具體控制權。排程或事件觸發、持續監看、多人核准是第 4–6 種都可能採用的**啟動與管理方式**，不是另一種產出。第 5、6 種也可設定為只讀、只建草稿，或經人核准後寫入系統；**接手範圍**與**寫入權限**需要分開記。

這些用法**可以先後相接**：先由 Agent 寫腳本，腳本遇到例外時再呼叫一次模型或一個 Agent；節點 Agent 也可能只提出建議，等人核准才寫入系統。因此分類要針對**當下這件工作**，標明「交出哪段工作、誰觸發、當時是否呼叫模型、模型能否選步驟／工具、會不會寫入外部狀態、何時交給人、誰接手」。尤其「Agent 寫了程式後就退出」只適用於後續程式沒有再呼叫模型的情況；程式若在執行時呼叫模型，便有模型參與流程，但是否構成 Agent 還要看它能否選擇步驟與工具。

## 洞見

- **中間產物是找缺口的最佳切點。** 看一件工作需要哪些查詢式、欄位表、草稿、程式、工具參數和驗收紀錄，就能問哪些步驟最耗時、最容易掉脈絡；只看最後成品會漏掉工作量。
- **業務動詞有完成條件。** 「發布」要問發布到哪裡、用哪版、誰核准、是否送達；「維護」要問故障是否排除、資料是否恢復；「解釋」要問使用者是否理解且未被誤導。Agent 完成一個工具呼叫，只能證明那一步，不能直接宣稱整項業務完成。
- **人機分工不是整個動詞一刀切。** 同一動詞中可能同時有適合 Agent 的查找、比對、草擬，也有專業判定、外部發布或現場處置。應逐段看輸入、產物、標準與責任。

## 附錄：未採用的展開（2026-09-19 前的版本）

以下保留原四層對照、操作分類、業務動詞對照與兩個完整案例，作為演變紀錄與講師參考。「三條界線」（寫出指令不等於執行、建議不等於決定、送出不等於接手）與前段重複，已改為 [[agent-use-patterns]] 的一句提醒與工作坊表的「完成證據」欄。

#### 先區分四層

```text
第 1 層　具體操作：拆解、讀、查、抽、比、算、寫、執行、詢問、通知、檢查、追蹤
              ↓ 組合並留下
第 2 層　中間產物：查詢式、欄位表、差異清單、草稿、程式、API 參數、測試紀錄
              ↓ 經工具執行與驗收成為
第 3 層　可交付的產出：內容、資料、程式、系統狀態、訊息、持續服務、知識資產
              ↓ 放進有目的、責任與標準的流程，才構成
第 4 層　業務動詞：守視、查核、發布、解釋、提供、整理、分析、維護、協調、管考
```

這條箭頭**不是一對一對照**。同一個操作可支援多種產出；同一種產出可服務多個業務動詞；一個業務動詞往往需要多項產出和人員判斷。Agent 的價值不由動作數量決定，而由整段工作是否達到業務標準決定。

#### 第 0 層：操作能發生的條件

在操作之前，必須先有**觸發方式、可取得的資料、可呼叫的工具、執行環境、權限、工作規則與驗收標準**。例如「寄信」需要郵件工具和寄送權限；「產 PPTX」需要能寫檔與生成簡報的程式庫或應用；「檢查測站」需要有權讀取的狀態資料。Skill／說明文件可教做法，不能替代資料、工具或授權。[OpenClaw 工具文件](https://docs.openclaw.ai/tools)也把工具、Skill 與插件分開。

#### 第 1 層：Agent 可組合的具體操作

「規劃下一步」本身不保證業務成果；它要落成可檢查的子任務、查詢、工具參數或交接要求。下表同時列出模型在上下文中做的安排，與外部工具可觀察的動作。

| 操作族 | 可觀察的具體動作 | 常見中間產物或工具回饋 | 能力邊界 |
|---|---|---|---|
| **接收與觸發** | 接收訊息、檔案、事件；依排程開始或恢復工作 | 任務、觸發時間、來源、執行紀錄 | 排程到點只代表開始，未代表完成 |
| **理解與拆解** | 確認目標和限制、拆子任務、選資料與工具、設定停止或轉交條件 | 工作步驟、待確認問題、工具選擇、驗收條件 | 計畫須能因工具結果修正；不能把計畫當成完成 |
| **讀取與查找** | 讀檔、查資料庫、搜尋文件與網頁、讀畫面或系統狀態 | 查詢式、來源清單、原始摘錄、時間戳 | 讀取權限和資料範圍須先確認 |
| **擷取與整理** | 從文件抽欄位、轉格式、去重、分類、索引、串同一事件 | 欄位表、分類標籤、對照鍵、資料缺漏清單 | 格式一致不代表內容正確 |
| **比較與計算** | 比版本、對規則、算統計、找異常、執行既有演算法 | 差異表、數值、程式輸出、待查案例 | 科學判定需領域標準；數值應可重算 |
| **產生內容** | 草擬文字、圖表、圖片、網頁、簡報頁、回答或建議 | 文稿、圖稿、逐頁稿、提示／生成參數 | 草稿不等於已核准或已發布 |
| **產生可執行材料** | 寫程式、SQL、腳本、設定、API 參數、操作序列 | 程式碼、patch、命令、JSON 請求、瀏覽器動作計畫 | 寫出指令不等於執行成功 |
| **執行與寫入** | 執行程式、呼叫 API、操作瀏覽器、建立工單、修改檔案或系統紀錄 | 工具回傳值、事件／工單 ID、diff、更新後狀態 | 依授權工具與環境而定；可回復性須檢查 |
| **傳送與交接** | 發訊息、寄信、提交表單、交給下一人或另一 Agent | 寄送 ID、收件對象、交班摘要、待辦狀態 | 送出、送達與接手是三件事 |
| **詢問與協作** | 向人補問資料、提出選項、要求核定、接收退件與修正意見 | 問題、決定、批准紀錄、退件原因 | 人的沉默不等於核准；責任須可追溯 |
| **驗證與修正** | 重新讀狀態、測試程式、渲染成品、核對來源、比較預期與實際 | 測試報告、截圖、錯誤訊息、驗收紀錄 | 遇錯可退回前一步；高影響事項由人判斷 |
| **持續追蹤與回存** | 定期重查、追蹤未完成事項、保存來源與決定、更新規則或知識 | 排程、狀態差異、日誌、KB／SOP 修訂 | 必須有停止條件、過時清理與維護者 |

表中「比較與計算」「產生內容」可由模型、一般程式、專業演算法或人共同完成；Agent 的特色是**在回饋下選擇和串接步驟**，而不是每個步驟都由模型計算。[Anthropic 的 Agent 說明](https://www.anthropic.com/engineering/building-effective-agents)也強調工具結果作為後續步驟的依據。

#### 第 2、3 層：中間產物如何變成最後交付

| 中間產物與執行路徑 | 可交付產出 | 最常見的驗收問題 |
|---|---|---|
| 摘錄、綱要、逐頁稿 → 排版程式／簡報軟體 → 檔案 | **給人看的內容**：報告、圖文、PPTX、網頁、影音 | 內容與來源正確嗎？檔案能開、能讀、能用嗎？ |
| 文件擷取規則、欄位表 → 比對／清理 → 匯出 | **給系統用的資料**：JSON、CSV、索引、標籤 | 欄位定義、漏件、口徑與版本可查嗎？ |
| 需求、程式碼、測試與設定 → 執行環境 | **可執行成果**：腳本、應用、查詢、可重用流程 | 測試通過嗎？運行條件與失敗方式清楚嗎？ |
| 草稿、證據、選項 → 人員審核 | **判斷材料**：差異、異常、原因假說、建議 | 依據和不確定性寫明了嗎？人是否真的核定？ |
| API 參數／瀏覽器動作 → 工具執行 → 回讀狀態 | **系統狀態改變**：檔案、工單、資料庫、設定 | 寫到正確目標嗎？有 ID、日誌和回復方式嗎？ |
| 收件對象、內容與時機 → 傳送工具 → 送達回饋 | **通知與交接**：信、訊息、待辦、通報 | 對的人收到並知道下一步嗎？ |
| 排程、查詢條件、差異門檻 → 反覆執行 | **持續服務**：監看、提醒、定期摘要 | 誤報、漏報、重複與停止條件可控嗎？ |
| 經核實的經驗、適用條件與版本 → 回存 | **知識資產**：FAQ、SOP、檢查表、Skill | 下次找得到、用得對、有人維護嗎？ |
| 當前問題、檢索結果、回饋 → 多輪答覆 | **互動服務**：問答、引導、即時協作 | 每輪是否依最新情況答覆？何時轉交人？ |

第 3 層是**產出形態**，不是使用率排名；同一工作可能留下多項成果。原先「投影片、程式碼、控制某個程式」三例，分別落在內容、可執行成果、系統狀態改變；第三例特別需要區分產生命令與執行後回讀。

#### 第 4 層：接到地震業務的工作動詞

| 業務動詞 | 可組合的底層操作 | 可能交付與交接 | 人的權責位置 |
|---|---|---|---|
| **守視、發現** | 定期／即時讀狀態、比門檻與歷史、標記異常 | 狀態面板、待查清單、提醒 | 同仁判斷是否為有效事件或設備異常 |
| **查核、判定** | 查來源、比版本、重算、列差異與疑點 | 有依據的查核底稿、待判清單 | 由有權責者確認地震資訊與發布判定 |
| **通報、發布、更新** | 套正式資料、產文稿、核准、傳送、回查、留版本 | 報告、通報紀錄、網站版本 | 正式發布、重大事件通報與科學責任依既定制度 |
| **回答、解釋、宣導** | 檢索已發布資訊、按受眾轉寫、製圖、查證 | 答覆、FAQ、圖文／簡報草稿 | 專業內容、對外措辭與例外答覆需審核 |
| **提供資料、支援使用** | 查資料、過濾、轉格式、附口徑與使用說明 | 資料集、索引、查詢結果 | 確認可提供範圍與資料定義 |
| **整理、校對、保存** | 擷取、去重、比對、驗證、備份與更新索引 | 目錄、統計底稿、版本紀錄 | 決定校訂與正式資料版本 |
| **分析、報導、研究** | 蒐集、計算、視覺化、草擬、查反例 | 月報／年報草稿、圖表、研究底稿 | 研究設計、科學解釋與署名責任 |
| **維護設備與場站** | 讀測站狀態、關聯維修史、建待修單、追進度 | 異常卡、工單、維修紀錄 | 現場檢修與設備處置由人員負責 |
| **維護、改進資訊系統** | 查日誌、定位問題、寫程式／設定、測試、部署後監看 | patch、測試紀錄、版本與系統狀態 | 系統變更審核、上線與回退決定 |
| **規劃、協調、管考** | 比計畫與成果、整理會議、追待辦、提醒與回存 | 進度表、決議紀錄、對照報告 | 資源分配、對外承諾及績效判定 |

這是**用途對照與訪談假說**，不表示中心現行採用 Agent 或有同名缺口。以[官網職掌](https://scweb.cwa.gov.tw/zh-tw/page/intro/6)為業務範圍依據，實際流程與人機分工必須從同仁的具體事件重建。

#### 走完一個例子：測站異常待查

1. **觸發／讀取**：從可授權的測站狀態、通訊日誌或維運紀錄取得最新資料。中間產物是含時間戳的觀測清單。
2. **比較／查找**：與基準及近期維修紀錄比對，列出資料中斷時間、受影響範圍與替代解釋。產物是待查異常卡；不能只憑一個訊號認定設備故障。
3. **人員確認**：值班或維運同仁確認問題、優先度與負責人。Agent 可列證據，不能代替現場檢修。
4. **執行／交接**：若流程允許，Agent 依核准內容建立工單並通知承辦人；回讀工單 ID 與送達狀態。業務動詞從「守視」接到「維護、協調」。
5. **追蹤／回存**：定期查處理進度，恢復後把受影響時段、原因和解法連回紀錄。業務動詞再接到「整理、保存」。

這是**示例設計**，公開資料尚不足以確認中心目前的測站告警、工單或交班系統，也不代表已授權 Agent 接入。

#### 再走一個例子：對民眾解釋地震資訊

已發布報告與 FAQ → 檢索、核對發布時間與版本 → 產生面向民眾的文字／圖文草稿 → 專業人員確認與核准 → 回答或發布 → 保存問答與更正。此例同時產生**判斷材料、內容、對話答覆與可能的知識資產**；「解釋」是整段服務，並非模型寫出一句話就完成。
